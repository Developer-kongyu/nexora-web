# 第二阶段独立学习指南：从 HTML 入口到页面显示

本文对应[《代码系统学习方案》](./代码系统学习方案.md)的第二阶段，把原来第 6～10 次学习合并成一份可以从头连续学完的教材。讲解以当前项目源码为依据，核对日期为 2026-09-17。

你将完整走通：

```text
浏览器取得 index.html
  → main.ts 发起启动
  → bootstrapApplication 找挂载点、加载应用、处理启动失败
  → mountApplication 按需启动 Mock，并交给 React 渲染
  → ApplicationRoot 组织根组件
  → AppProviders 提供查询、提示以及认证/实时初始化
  → AppRouter 匹配 URL
  → 访问守卫决定显示、等待还是跳转
  → Layout 的 Outlet 显示目标页面
```

这条线是职责关系。前半段有明确的 `await` 顺序；React 渲染后的认证恢复、实时连接、页面请求则不能全部理解成“上一步彻底结束，下一步才执行”。

本文包含必要的语法补课、真实源码讲解、URL 视图实验、检查清单和参考答案。**阅读本身不需要改业务代码；第七节明确标出练习时需要新增或修改的内容。**

## 二、阅读源码前，补齐最必要的语法

### 2.1 文件、模块、组件不是同一个概念

**文件**是磁盘上的文件，例如 `main.ts`。**模块**是通过 `import` 和 `export` 组织的代码单元。**组件**则是 React 用来描述界面的函数等对象，一个文件可以导出一个或多个组件，也可以完全不包含组件。

```ts
import { bootstrapApplication } from '@/app/bootstrapApplication';
```

意思是：从目标模块取出名为 `bootstrapApplication` 的导出，供当前模块使用。这里的花括号对应“具名导入”。

`@` 是项目配置的路径别名。该例对应 [src/app/bootstrapApplication.ts](../src/app/bootstrapApplication.ts)，不是一个名为 `@` 的真实文件夹。Vite 的别名配置见 [vite.config.ts](../vite.config.ts)，TypeScript 的路径配置见 [tsconfig.base.json](../tsconfig.base.json)。

```ts
import '@/app/styles/global.css';
```

这个导入没有接收变量，目的是让构建工具把全局样式纳入页面。它与 `import styles from './Something.module.css'` 的用法不同：后者接收 CSS Modules 的类名映射，本行只是加载全局 CSS。

### 2.2 函数本身与执行函数

先记住这组区别：

```ts
onRetry                    // 取得函数本身，暂时不执行
onRetry()                  // 现在执行函数
() => window.location.reload() // 创建一个函数，调用它时才刷新
```

项目中：

```ts
onRetry: () => window.location.reload(),
```

冒号左边是对象的属性名；右边是一个函数值。不是“启动时立即刷新页面”，而是“把以后重试时该做的事交给启动流程”。

如果写成 `onRetry: window.location.reload()`，就会在创建这个对象时立即执行刷新，含义完全不同。

同样：

```ts
return application.mountApplication;
```

返回的是挂载函数。稍后 `bootstrapApplication` 才会执行 `mountApplication(root)`。

### 2.3 对象、解构、默认值

```ts
const options = {
  rootId: 'root',
  onRetry: () => window.location.reload(),
};
```

这是一个对象，包含两个属性。

```ts
const { rootId, onRetry } = options;
```

是对象解构，分别取出同名属性。它等价于分别写 `options.rootId` 和 `options.onRetry`。

函数参数也可以解构：

```ts
function example({ rootId = 'root' }: { rootId?: string }) {
  return rootId;
}
```

可按三个部分理解：

- `{ rootId = 'root' }`：从传入对象里取出 rootId，缺失或为 undefined 时使用默认值。
- `: { rootId?: string }`：TypeScript 类型说明；问号表示这个属性可不传。
- 最后的 `{ return rootId; }`：函数体，调用时执行。

**并非所有花括号都是同一种语法。** 在本项目里，它可能表示对象、解构、函数体，或 JSX 中的 JavaScript 表达式。先看它所在位置。

### 2.4 Promise、async、await

Promise 可以理解成“一个将来得到成功结果或失败原因的异步结果对象”。

```ts
const mountApplication = await loadApplication();
await mountApplication(root);
```

第一行：调用加载函数，等待它给出挂载函数，再把这个函数存到变量里。

第二行：执行刚拿到的挂载函数，等待其返回的 Promise 完成。

`async` 函数总是返回 Promise；`await` 暂停的是当前异步函数的后续执行，不是冻结整个浏览器。

```ts
(root: HTMLElement) => Promise<void>;
```

这是**函数类型**：接收一个 HTML 元素，返回 Promise；Promise 成功时没有需要交给调用方的业务值。这里的 `void` 不等于“函数什么都不做”。

`try / catch` 能接住对应代码块里抛出的同步错误，以及被 `await` 的 Promise 拒绝。未来某个点击事件或另一个未等待的异步任务报错，不能仅因为“它起源于这次启动”就自动归入这个 catch。

### 2.5 类型说明不会创建页面元素

```ts
root: HTMLElement
document: Document
error?: unknown
```

它们分别表示“HTML 元素”“文档对象”“可省略、类型暂不确定的错误值”。这些是 TypeScript 在开发期间提供的约束，不是在浏览器里新建 DOM 的命令。

```ts
type BootstrapApplicationResult = 'mounted' | 'failed' | 'missing-root';
```

这里的竖线表示“允许是这些值中的一个”，不是字符串拼接。

`.ts` 通常放 TypeScript 逻辑；`.tsx` 允许在 TypeScript 里写 JSX。组件文件经常使用 `.tsx`，但像 `mountApplication.ts` 这样调用 `createElement`，也可以不写 JSX。

### 2.6 JSX 中看起来像 HTML 的东西

```tsx
<AppProviders>
  <AppRouter />
</AppProviders>
```

这是 JSX，用来描述 React 元素。大写开头的标签对应组件；小写的 `div`、`button` 等对应浏览器元素。

`<AppRouter />` 是自闭合写法；它没有直接写在标签中间的子内容。

```tsx
function Wrapper({ children }: { children: React.ReactNode }) {
  return <main>{children}</main>;
}
```

上面是说明用的简化例子：

- `children` 是嵌套在组件标签中间、传给该组件的内容。
- `ReactNode` 是 React 能渲染的内容类型，可以是元素、文字、数组、null 等。
- JSX 里的 `{children}` 表示在这里放入 JavaScript 表达式的结果。

`children` 不会因为名字存在就自动出现在页面上；包装组件需要在返回值中使用或返回它。

### 2.7 三元表达式、提前返回与可选链

```ts
const view = params.get('view') === 'compact' ? 'compact' : 'detailed';
```

读作：“如果左边条件成立，取 compact；否则取 detailed。”

```ts
if (!mockMode || !env.VITE_ENABLE_MOCK) return;
```

`!` 表示逻辑取反，`||` 表示或；任一条件成立就结束这个函数，因此后面的 Mock 启动语句不会执行。

```ts
user?.onboardingCompleted;
```

`?.` 是可选链：当 user 为 null 或 undefined 时，不继续读取其属性，表达式结果为 undefined。它与类型定义中的 `rootId?: string` 不是同一种用法。

现在可以开始沿着真实入口读代码了。

## 三、启动链路：从 index.html 到 React 根

### 3.1 index.html：最初浏览器里有什么

[源码：index.html](../index.html) 的关键部分：

```html
<body>
  <div id="root"></div>
  <script type="module" src="/src/app/main.ts"></script>
</body>
```

第一行的 div 是挂载容器。它最初没有子元素，因此还没有首页、导航栏或登录表单。

第二行告诉浏览器加载模块脚本。开发时浏览器通过 Vite 服务访问页面，Vite 会把 TypeScript 等源文件转换成浏览器可执行的模块；浏览器不是天然认识任意 TypeScript 语法。构建后的 HTML 会引用构建产物，也不要求生产浏览器直接下载这个源文件路径。

所以应通过开发服务器打开页面，而不是双击磁盘上的 index.html。

把这两个概念分开：

- `id="root"`：DOM 元素的标识。
- `src="/src/app/main.ts"`：开发时的脚本入口地址。

它们通过后面的 `getElementById('root')` 和 React 挂载代码发生联系，并非浏览器见到 root 这个名字就自动启动 React。

### 3.2 main.ts：把启动所需能力交给启动函数

[源码：main.ts](../src/app/main.ts) 全文：

```ts
import { bootstrapApplication } from '@/app/bootstrapApplication';
import '@/app/styles/global.css';

void bootstrapApplication({
  document,
  loadApplication: async () => {
    const application = await import('@/app/mountApplication');
    return application.mountApplication;
  },
  onRetry: () => window.location.reload(),
  reportError: (message, error) => console.error(message, error),
});
```

先看传入的对象：

| 属性            | 传入什么       | 启动流程何时使用                 |
| --------------- | -------------- | -------------------------------- |
| document        | 当前浏览器文档 | 查找挂载点                       |
| loadApplication | 一个异步函数   | 挂载点存在后，加载真正的应用模块 |
| onRetry         | 刷新页面的函数 | 启动失败页的重试按钮被点击时     |
| reportError     | 输出错误的函数 | 缺少挂载点或启动失败时           |

`document,` 是对象属性简写，相当于 `document: document,`。

`console.error(message, error)` 会输出到开发者工具控制台，当前这一行没有接入远程错误上报服务。

开头的 `void` 表示调用方不使用这个 Promise 表达式的结果。**它不等于 await，不负责捕获异常，也不是屏蔽报错。** 本项目预期的加载/挂载错误由下一节的 try/catch 处理。

### 3.3 动态导入为什么返回一个函数

单独展开 main 中这段：

```ts
loadApplication: async () => {
  const application = await import('@/app/mountApplication');
  return application.mountApplication;
},
```

这里发生三件事：

1. 真正调用 loadApplication 时，执行 `import(...)`。
2. 等待模块加载和求值，得到包含导出内容的模块对象 application。
3. 从模块对象中取出名为 mountApplication 的导出，并把它返回。

可以把 application 想象成这种形状，注意这是帮助理解的示意：

```ts
{
  mountApplication: 某个挂载函数;
}
```

动态导入是异步的，可以在需要时再加载模块，也能让本项目在这一步失败时进入启动回退。模块加载与求值还会涉及它的静态依赖，例如 ApplicationRoot、AppProviders、router、env；这些依赖加载或求值失败，也可能使本次 import 拒绝。动态导入不是“每次调用都绕过缓存重新下载”；模块加载有缓存机制。相关语义见 [MDN：import()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import)。

与后面路由懒加载相比，这里延后加载的是应用挂载模块；路由懒加载延后加载的是匹配到的页面模块，两者的边界不同。

### 3.4 bootstrapApplication 的类型声明：先看合同

[源码：bootstrapApplication.ts](../src/app/bootstrapApplication.ts)：

```ts
export type ApplicationMount = (root: HTMLElement) => Promise<void>;

export interface BootstrapApplicationOptions {
  document: Document;
  loadApplication: () => Promise<ApplicationMount>;
  onRetry: () => void;
  reportError: (message: string, error?: unknown) => void;
  rootId?: string;
}

export type BootstrapApplicationResult = 'mounted' | 'failed' | 'missing-root';
```

这里没有执行启动，只是在定义调用约定。

最容易读错的一行是：

```ts
loadApplication: () => Promise<ApplicationMount>;
```

分层读：

```text
loadApplication 是一个函数
  → 调用后得到 Promise
  → Promise 成功时得到 ApplicationMount
  → ApplicationMount 又是一个函数
  → 这个函数接收 root，返回 Promise<void>
```

它不是“传入一个组件”，也不是“传入一个 HTML 元素”，而是“传入一个将来能提供挂载函数的加载器”。

这种设计让启动函数不必自己写死浏览器全局对象、动态导入位置、刷新行为和错误记录方式。测试时也就能传入替代实现。

### 3.5 bootstrapApplication 的执行体：三条路径

同一文件的函数体：

```ts
export async function bootstrapApplication({
  document,
  loadApplication,
  onRetry,
  reportError,
  rootId = 'root',
}: BootstrapApplicationOptions): Promise<BootstrapApplicationResult> {
  const root = document.getElementById(rootId);
  if (!root) {
    reportError(`Application bootstrap failed: missing #${rootId} element.`);
    return 'missing-root';
  }

  try {
    const mountApplication = await loadApplication();
    await mountApplication(root);
    return 'mounted';
  } catch (error) {
    reportError('Application bootstrap failed.', error);
    renderBootstrapFailure(root, { onRetry });
    return 'failed';
  }
}
```

逐步跟读：

1. 参数解构后，未提供 rootId 时使用字符串 `'root'`。
2. `document.getElementById(rootId)` 查找真实 DOM；找到返回元素，找不到返回 null。
3. 如果不存在，记录错误，立即返回 missing-root。这种情况下不会调用 loadApplication，也没有容器可用来显示本项目的启动失败页。
4. 存在时进入 try，等待加载器提供挂载函数。
5. 把真实 root 交给挂载函数，并等待该函数的 Promise。
6. 这两步成功后返回 mounted。
7. 加载或挂载 Promise 失败时，进入 catch：记录错误、创建启动失败 DOM、返回 failed。

表格复盘：

| 条件                       | 是否加载应用 | 是否尝试挂载 | 结果                     |
| -------------------------- | ------------ | ------------ | ------------------------ |
| 没找到 root                | 否           | 否           | missing-root，并记录错误 |
| 找到 root，加载失败        | 是，但失败   | 否           | failed，显示启动失败页   |
| 加载成功，挂载函数失败     | 是           | 是，但失败   | failed，显示启动失败页   |
| 加载成功，挂载函数正常返回 | 是           | 是           | mounted                  |

`mounted` 是这个函数定义的状态名称：表示挂载函数已经正常返回。它也不保证首屏 DOM 已提交或浏览器已经绘制，更**不是**“所有组件的 Effect 已完成、认证已恢复、接口数据已取回”的证明。

### 3.6 mountApplication：准备 Mock，再交给 React

[源码：mountApplication.ts](../src/app/mountApplication.ts) 全文：

```ts
import { createElement } from 'react';
import { createRoot } from 'react-dom/client';
import { ApplicationRoot } from '@/app/ApplicationRoot';
import { env } from '@/shared/config/env';

async function enableMocking(): Promise<void> {
  const mockMode = import.meta.env.DEV || import.meta.env.MODE === 'test';
  if (!mockMode || !env.VITE_ENABLE_MOCK) return;

  const { worker } = await import('@/mocks/browser');
  await worker.start({
    onUnhandledRequest: import.meta.env.MODE === 'test' ? 'error' : 'bypass',
    serviceWorker: { url: '/mockServiceWorker.js' },
  });
}

export async function mountApplication(root: HTMLElement): Promise<void> {
  await enableMocking();
  createRoot(root).render(createElement(ApplicationRoot));
}
```

先只看最后三行：

```ts
await enableMocking();
createRoot(root).render(createElement(ApplicationRoot));
```

为什么先 await？因为认证恢复、页面请求可能在应用开始渲染后很快发生。如果 Mock 要用来拦截这些请求，就需要先完成 worker 启动，避免先发出一批未被 Mock 接管的请求。

如果条件不允许使用 Mock，enableMocking 会提前返回；因为它是 async 函数，这仍然对应一个正常完成的 Promise。

第二行可以为了理解而拆成：

```ts
const reactRoot = createRoot(root);
const applicationElement = createElement(ApplicationRoot);
reactRoot.render(applicationElement);
```

| 表达式                         | 得到什么                        | 不是哪一个东西                         |
| ------------------------------ | ------------------------------- | -------------------------------------- |
| root                           | 浏览器中的挂载 DOM 元素         | 不是 React 组件函数                    |
| createRoot(root)               | 管理该容器内容的 React 根对象   | 不是另一个新建的 div                   |
| ApplicationRoot                | 项目定义的根组件函数            | 不是挂载容器                           |
| createElement(ApplicationRoot) | 描述要渲染哪个组件的 React 元素 | 不是 document.createElement 创建的 DOM |
| reactRoot.render(...)          | 提交要渲染的内容                | 不是等待所有后续异步任务结束的 Promise |

`createElement(ApplicationRoot)` 在这里表达的组件关系相当于 `<ApplicationRoot />`。使用前者就不需要在这个 .ts 文件内书写 JSX。

React 的 root.render 不是“调用返回时所有 Effect 都已经执行完毕”的同步屏障，因此前面启动函数返回 mounted 时，登录恢复可能仍在进行。见 [React：createRoot / root.render](https://react.dev/reference/react-dom/client/createRoot)。

### 3.7 Mock 的开关：需要同时满足两层条件

Mock 是用预设处理器模拟接口响应，帮助在学习、测试时运行应用。浏览器端初始化入口是 [mocks/browser.ts](../src/mocks/browser.ts)。

源码条件：

```ts
const mockMode = import.meta.env.DEV || import.meta.env.MODE === 'test';
if (!mockMode || !env.VITE_ENABLE_MOCK) return;
```

换成直白的话：

```text
处于开发环境，或者 Vite mode 名为 test
并且
项目解析后的 VITE_ENABLE_MOCK 为 true
才会启动浏览器 Mock
```

| 情况                                  | 常规情况下是否启动           |
| ------------------------------------- | ---------------------------- |
| 开发运行，但开关为 false              | 不启动                       |
| 开发运行，开关为 true                 | 启动                         |
| 使用 test mode，开关为 true           | 启动                         |
| 正常 production 构建，即使开关为 true | 不启动，因为第一层条件不满足 |

这里的 `MODE` 与 `DEV` 不完全相同；`--mode test` 选择 test 模式配置，不等于“正在执行 Vitest 单元测试”。Vite 对 mode 与开发/生产环境的说明见 [Vite：Env Variables and Modes](https://vite.dev/guide/env-and-mode)。

还要注意字符串和布尔值：

```ts
VITE_ENABLE_MOCK: z
  .enum(['true', 'false'])
  .default('false')
  .transform((value) => value === 'true'),
```

这段来自 [env.ts](../src/shared/config/env.ts)。环境变量最初是字符串，经过校验和转换，`env.VITE_ENABLE_MOCK` 才是布尔值。不能直接把字符串 `'false'` 当成布尔 false，因为非空字符串在条件判断中为真。

worker.start 的两个选项：

- `serviceWorker.url`：注册所使用的脚本地址，对应 [public/mockServiceWorker.js](../public/mockServiceWorker.js)。
- `onUnhandledRequest`：test mode 为 error，未匹配 Mock 的请求会按错误策略处理；其他允许 Mock 的模式为 bypass，会让未匹配请求继续走真实网络。它不表示所有请求都自动有模拟数据。

### 3.8 把执行顺序和组件关系分成两张图

第一张是启动函数的执行过程：

```text
main 调用 bootstrapApplication
  ├─ 找不到 root → reportError → 返回 missing-root
  └─ 找到 root
       → await loadApplication()
       → await mountApplication(root)
            → await enableMocking()
            → createRoot(root).render(...)
       → 返回 mounted

try 内加载或挂载失败
  → reportError
  → renderBootstrapFailure
  → 返回 failed
```

第二张是 React 接下来要渲染的结构：

```text
ApplicationRoot
  → StrictMode
    → AppProviders
      → AppRouter
        → 当前路由对应的守卫、布局和页面
```

第二张中的箭头表示包含关系。它不能推导出“AuthBootstrap 请求完成之后才创建 AppRouter”。这一点在第四节会结合源码说明。

### 3.9 用现有测试验证你的理解

阅读 [bootstrapApplication.test.ts](../src/app/bootstrapApplication.test.ts)，先找三个测试的名字，再看断言：

| 测试场景           | 它证明什么                                                |

**停下来口答：**

1. main.ts 的 loadApplication 返回的是页面还是函数？

## 四、根组件与全局能力

这一节解决一个具体问题：页面为什么能直接使用数据查询、全局提示和认证状态，而不必在每一页都重新创建它们？读完后，你应能画出真实组件树，解释 `children` 的传递，预测恢复会话和实时连接的基本行为。

先认识两个词：**组件树**表示谁把谁渲染在里面；**副作用**表示渲染之外需要和外部系统交互的工作，例如 HTTP 请求、Socket 连接、定时器。组件树可以用嵌套 JSX 描述，副作用通常通过 `useEffect` 管理。它们是两种不同关系，不能把 JSX 从外到内读成一串 `await`。

### 4.1 先把根组件的 JSX 读懂

打开 [ApplicationRoot.tsx](../src/app/ApplicationRoot.tsx)，完整实现很短：

```tsx
import { StrictMode } from 'react';
import { AppProviders } from '@/app/providers/AppProviders';
import { AppRouter } from '@/app/router/router';

export function ApplicationRoot() {
  return (
    <StrictMode>
      <AppProviders>
        <AppRouter />
      </AppProviders>
    </StrictMode>
  );
}
```

逐段看：

- `export function ApplicationRoot()` 定义并导出一个 React 函数组件。React 调用它，取得它返回的界面描述。
- `<AppRouter />` 表示渲染路由组件。自闭合写法说明这个调用点没有给它传入嵌套内容。
- `<AppProviders>…</AppProviders>` 把路由组件作为嵌套内容交给 `AppProviders`，让路由下面的页面处在全局能力的作用范围内。
- `<StrictMode>…</StrictMode>` 为整棵子树启用 React 的开发检查。它不产生一个叫 `strictmode` 的 HTML 元素。
- 大写标签表示 React 组件；`<div>`、`<button>` 这样的标签才直接对应原生 DOM 元素。并不是每个组件都会额外生成一层 HTML。

`@/app/...` 是本项目配置的路径别名，指向 `src/app/...`，它与 JSX 嵌套本身没有关系。`import` 是拿到组件或函数，JSX 是描述把哪些组件放进界面。

### 4.2 `children` 是怎么进来的，`ReactNode` 又是什么

看 [AppProviders.tsx](../src/app/providers/AppProviders.tsx) 的 Props 定义：

```tsx
interface AppProvidersProps {
  children: ReactNode;
}

export function AppProviders({ children }: AppProvidersProps) {
```

这里的 `children` 是一个普通的 Props 字段，只是 JSX 对嵌套内容采用了这个约定名称。下面两种调用在这个例子里表达相同意思：

```tsx
<AppProviders>
  <AppRouter />
</AppProviders>
```

```tsx
<AppProviders children={<AppRouter />} />
```

`{ children }` 是对象解构：从传入的 Props 对象里拿出 `children`。`: AppProvidersProps` 是 TypeScript 类型标注，在开发和检查时约束这个对象的形状，并不会在运行时创建一个额外对象。

`ReactNode` 可以理解成“React 可以处理的子内容”的类型，常见例子有 JSX 元素、文字、数字、节点数组和 `null`；布尔值也可以作为节点参与表达式，但不会显示成文字。它比“只能放一个 JSX 元素”更宽。**类型负责检查输入，实际显示什么取决于组件的返回值。**

例如 `AuthBootstrap` 最后写的是：

```tsx
return children;
```

这表示把收到的子内容继续交给 React 渲染，不额外增加一个 DOM 容器。如果包装组件收到了 `children` 却没有在返回值里使用它，里面的内容就不会自动出现。

你可以先用一句话读懂这类组件：“我接收一段子树，为它安排一些共同能力，再把它放进自己的返回结果。”至于“共同能力”是不是 Context，必须继续看实现，不能只看文件名里有没有 `Provider`。

### 4.3 画出项目实际的 Provider 树

[AppProviders.tsx](../src/app/providers/AppProviders.tsx) 的核心代码是：

```tsx
return (
  <QueryClientProvider client={queryClient}>
    <ToastProvider>
      <AuthBootstrap>
        <RealtimeProvider>{children}</RealtimeProvider>
      </AuthBootstrap>
    </ToastProvider>
    {import.meta.env.DEV ? <ReactQueryDevtools initialIsOpen={false} /> : null}
  </QueryClientProvider>
);
```

把上一节传入的 `<AppRouter />` 代入 `children`，得到下图。这里采用文本树，表示包含关系：

```text
ApplicationRoot
└─ StrictMode
   └─ AppProviders
      └─ QueryClientProvider：共享同一个 queryClient
         ├─ ToastProvider：提供 showToast，渲染提示区域
         │  └─ AuthBootstrap：启动认证恢复，继续返回 children
         │     └─ RealtimeProvider：按认证状态管理实时连接
         │        └─ AppRouter：根据 URL 渲染守卫、布局、页面
         └─ ReactQueryDevtools：仅 import.meta.env.DEV 为 true 时渲染
```

几个位置值得亲手在源码中确认：

1. `RealtimeProvider` 在 `QueryClientProvider` 内，所以它能调用 `useQueryClient()`。
2. 路由下面的页面都在 `ToastProvider` 内，所以页面能通过 `useToast()` 取得当前提示方法。
3. Query Devtools 在 Query Provider 内，但与 ToastProvider 同级。它不属于 `AuthBootstrap` 的子树，也不必等认证成功才出现；`initialIsOpen={false}` 表示工具面板初始收起。
4. `import.meta.env.DEV ? A : null` 是条件表达式：开发环境显示 A，否则不渲染这一项。这是 Vite 提供的构建环境信息。

下表区分“放在根上的包装组件”和“通过 Context 传值”：

| 这一层              | 当前项目做了什么                              | 是否在自己的实现里提供 Context 值         |
| ------------------- | --------------------------------------------- | ----------------------------------------- |
| QueryClientProvider | 让后代 Query hooks 取得同一个 QueryClient     | 是，由 TanStack Query 提供                |
| ToastProvider       | 保存当前提示、提供 `showToast`、渲染提示区域  | 是，使用 ToastContext.Provider            |
| AuthBootstrap       | 在 effect 中注册刷新处理器并发起会话恢复      | 否；状态写入 Zustand 的 useAuthStore      |
| RealtimeProvider    | 订阅认证状态，建立/清理通知连接，触发缓存失效 | 否；使用已有的 Query Context 和认证 store |

所以“外层先恢复登录，恢复完了才执行内层实时 Provider，最后才开始渲染路由”不是这段 JSX 的执行规则。真实情况是：这些组件参与渲染，各自根据自己的状态和 effect 条件开展工作。依赖先后由具体代码建立，例如实时 effect 检查 `status === 'authenticated'`。

### 4.4 Query Provider：共享缓存和默认行为

先认识 QueryClient：它是 TanStack Query 管理服务器数据缓存、查询状态和相关操作的对象。页面使用 `useQuery` 时，通常从上层 Provider 取得它，不需要手工一路传 Props。

[queryClient.ts](../src/shared/api/queryClient.ts) 的完整配置如下：

```ts
export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      gcTime: 10 * 60_000,
      retry: (count, error) => error instanceof ApiError && error.httpStatus >= 500 && count < 2,
      refetchOnWindowFocus: false,
    },
    mutations: { retry: false },
  },
});
```

模块顶层创建这个对象，再由 `AppProviders` 导入传给 Provider。这样在通常的运行过程中，组件重新渲染不会每次都创建一个新的 QueryClient。这里也没有配置把缓存持久化到浏览器存储；刷新整个页面不能假定旧的内存 Query 缓存仍然保留。

| 配置                          | 本项目默认行为                                             | 容易误读的地方                                                         |
| ----------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| `staleTime: 30_000`           | 查询数据在 30 秒内默认视为新鲜                             | 不是每 30 秒定时请求；过期本身也不意味着立即清空数据                   |
| `gcTime: 10 * 60_000`         | 查询不再被使用、成为非活跃缓存后，默认保留约 10 分钟再回收 | 不是“从获取成功起 10 分钟，无论有没有组件在用都删除”                   |
| `retry: ...`                  | 只有 `ApiError` 且 httpStatus ≥500 才按 `count < 2` 重试   | 404、普通 Error 都不满足；默认最多追加 2 次尝试，即同一轮最多 3 次执行 |
| `refetchOnWindowFocus: false` | 不因窗口重新获得焦点而按默认策略自动重取                   | 不会禁止主动 refetch 或其他重取触发方式                                |
| `mutations.retry: false`      | mutation 失败默认不自动重试                                | 不代表按钮不能让用户再次提交，也不改变底层其他请求逻辑                 |

Query 的“数据是否新鲜”与“没有人使用时何时回收”是不同维度，官方参数说明也分别定义了它们。[TanStack Query 的 useQuery 参数参考](https://tanstack.com/query/latest/docs/framework/react/reference/functions/useQuery)。

再看 `retry` 的三个条件：`instanceof ApiError` 要求错误确实是本项目的 API 错误对象；`httpStatus >= 500` 限定了这里愿意自动重试的状态范围；`count < 2` 限定次数。本项目安装的 Query 实现从 `count=0` 开始判断，因此第一次失败可重试，第二次失败还可重试，第三次失败停止。

这些是**默认值**，具体 `useQuery` 可以覆盖。它们也不是包住页面后就拦截所有网络请求：`AuthBootstrap` 直接调用 `authSession.refresh()` 和领域 API，没有通过 `useQuery`，因此不能拿这里的查询重试规则解释它的所有请求次数。

本阶段只需掌握“同一个缓存管理对象被共享”和“默认策略的含义”。Query Key、服务端 DTO、缓存刷新细节留到下一阶段继续读。

### 4.5 用 Toast 看懂 Context 真正提供了什么

Context 适合让后代组件读取某个共同值，而不用每经过一个中间组件都再传一次 Props。这里共享的不是所有提示列表，而是一个操作能力：`showToast`。

[ToastContext.ts](../src/shared/ui/Toast/ToastContext.ts) 定义：

```ts
export interface ToastContextValue {
  showToast: (toast: Omit<ToastMessage, 'id'>) => void;
}

export const fallbackToastContext: ToastContextValue = { showToast: () => undefined };
export const ToastContext = createContext<ToastContextValue | null>(null);
```

`Omit<ToastMessage, 'id'>` 表示“传入消息时不需要自己生成 id”。调用方给标题、tone 和可选说明，Provider 负责产生 ID。`createContext(...null)` 建立 Context；初始 null 表示没有找到上层提供值的组件。

[ToastProvider.tsx](../src/shared/ui/Toast/ToastProvider.tsx) 用 `useState` 保存提示数组、用 `showToast` 更新它，再把方法放进 Context。下面摘录提供值与渲染区域的关键部分，中间列表内容省略：

```tsx
const value = useMemo(() => ({ showToast }), [showToast]);

return (
  <ToastContext.Provider value={value}>
    {children}
    <div className={styles.viewport} aria-live="polite" aria-atomic="false">
      {/* 此处渲染 toasts 数组，对应源码中的 toasts.map(...) */}
    </div>
  </ToastContext.Provider>
);
```

这里同时发生两件事：Context Provider 让后代能读到 `showToast`；后面的真实 `<div>` 负责显示提示。Context 本身不是弹窗，也不会自动显示一条消息。`useMemo` 在 `showToast` 没改变时复用这个 value 对象，避免仅因为新建了对象而触发不必要的 Context 值变化。

[useToast.ts](../src/shared/ui/Toast/useToast.ts) 读取最近的同类 Provider：

```ts
export function useToast() {
  return useContext(ToastContext) ?? fallbackToastContext;
}
```

本项目有一个需要记住的特征：如果组件意外放到 ToastProvider 外面，`useToast()` 会给它一个无操作的 `showToast`，而不是在这里抛错。所以“点击没报错”不一定说明提示系统已经接好，真正证据是提示有没有渲染。

从现有 [ToastProvider.test.tsx](../src/shared/ui/Toast/ToastProvider.test.tsx) 可以读出使用方式：

```tsx
function ToastTrigger({ title }: { title: string }) {
  const { showToast } = useToast();

  return (
    <button type="button" onClick={() => showToast({ title, tone: 'info' })}>
      {`显示${title}`}
    </button>
  );
}
```

点击按钮后，事件处理函数调用 Context 中的方法；Provider 更新 state；React 重新渲染提示数组，界面出现提示。这是“后代通过共享方法影响祖先持有的 UI 状态”的具体例子，不需要子组件直接访问父组件内部的 `setToasts`。

当前提示最多同时显示 3 条，每条默认显示 3600ms。手工关闭、淘汰旧提示和 Provider 卸载时都会清除对应定时器。测试覆盖了自动消失、手动关闭、第四条淘汰第一条、卸载清理四种行为。本阶段可沿用第一阶段的定时器知识，不必逐行展开所有 ref。

### 4.6 AuthBootstrap：恢复会话，但不负责拦住整棵子树

[AuthBootstrap.tsx](../src/app/providers/AuthBootstrap.tsx) 有一个初学者特别容易漏看的结尾：

```tsx
return children;
```

它没有写“恢复中返回 null”或“恢复完成才返回 children”。它的职责是在 effect 中安排认证恢复，实际状态保存在 [authStore.ts](../src/domains/auth/model/authStore.ts)。store 初始状态为 `bootstrapping`，基本状态含义如下：

| 状态          | 含义                 | 本阶段如何理解                               |
| ------------- | -------------------- | -------------------------------------------- |
| bootstrapping | 还在恢复/确认会话    | 暂时不能把用户认定为匿名，也不能认定为已登录 |
| authenticated | 已建立本地认证会话   | 还需根据引导状态判断具体页面能否进入         |
| anonymous     | 当前没有可用认证会话 | 受保护页面由守卫决定跳转登录                 |

effect 的末尾是下面这段真实代码：

```tsx
authSession.configureRefresh(refreshHandler);
void authSession.refresh();
return () => authSession.unconfigureRefresh(refreshHandler);
```

三行分别表示注册刷新处理器、开始一次恢复、清理时撤销自己注册的处理器。`void` 表示这里不使用 Promise 的返回值，它不会把异步操作变成同步，也不等于取消请求；是否捕获错误要继续看被调用函数。

本阶段只追成功主线：

```text
effect 启动恢复
→ refreshHandler 等待 authApi.refresh()
→ 成功后 setRefreshedSession：先保存 token，并把状态设为 authenticated
→ 请求 usersApi.getCurrentUserCard()
→ 用户卡成功后 updateUser 补齐 handle、名称和头像
```

这串步骤是 `refreshHandler` 内部真实的异步先后关系。请与上一节的 JSX 包含树分开。**authenticated 在用户卡补全之前就会写入**，所以其他订阅认证状态的组件不必等用户卡读取结束才获知登录已恢复。

失败分支也只记必要的三项：

- refresh 失败：如果这次工作仍有效，转为 anonymous，不继续读取用户卡。
- refresh 成功但用户卡返回 401：转为 anonymous。当前用户卡请求关闭了递归 401 刷新，避免在这个恢复过程里套娃重试。
- refresh 成功但用户卡暂时 503：保留已恢复的会话，可先显示尚未补全的用户资料。

源码中的 `isCurrent()` 是“这个异步结果现在还允许提交吗”的检查。用户退出、换一轮恢复或清理旧处理器后，旧请求结果不应覆盖当前状态。本阶段知道它守住这个边界即可；代次、并发合并和完整认证合同属于第四阶段。

那么界面为什么仍可能显示“正在恢复会话”？去看 [guards.tsx](../src/app/router/guards.tsx)：

```tsx
if (status === 'bootstrapping') return <Bootstrapping />;
```

这是守卫自己的渲染选择。根组件和路由可以已经参与渲染，而具体受保护的布局/页面暂时被守卫的加载提示替代。读这两处 `return`，比只看 `AuthBootstrap` 的名字更能确定实际行为。

[AuthBootstrap.test.tsx](../src/app/providers/AuthBootstrap.test.tsx) 验证了“先存 token 再用它请求用户卡”、用户卡 503 保持认证、用户卡 401 清除认证且不递归刷新、refresh 失败不请求用户卡。测试为状态边界提供证据，不需要为了第二阶段把认证所有函数逐行背下来。

### 4.7 RealtimeProvider：为什么异步清理要有两道检查

[RealtimeProvider.tsx](../src/app/providers/RealtimeProvider.tsx) 先从两个地方取得依赖：

```tsx
const status = useAuthStore((state) => state.status);
const client = useQueryClient();
```

第一行订阅 Zustand 中的认证状态，状态变化会影响组件；第二行从上层 Query Provider 取得缓存管理对象。再看 effect 的启动部分：

```tsx
if (status !== 'authenticated') return;

let disposed = false;
let disconnect: (() => void) | null = null;
const connection = connectNotificationSocket(() => {
  void client.invalidateQueries({ queryKey: notificationKeys.all });
});
```

这里的 `return` 位于 effect 内，意思是这次不建立连接；组件在 effect 外仍然 `return children`，所以匿名用户的路由内容不会被它隐藏。

`connectNotificationSocket` 返回 `Promise<() => void>`。从里向外读：`() => void` 是一个不接收参数、不返回业务值的函数，在这里负责断开连接；`Promise<...>` 说明要等异步准备完成，才拿得到这个函数。

打开 [realtimeClient.ts](../src/domains/notifications/realtime/realtimeClient.ts) 可以确认：配置了 socket URL 时，它先请求通知 bootstrap，再调用 `io(...)`、注册事件监听，最后返回解绑/断开的函数。**这个 Promise 完成表示初始化流程拿到了清理函数，并不等于服务器已确认 websocket 握手成功。**没有配置 `VITE_SOCKET_URL` 时，它直接返回一个空清理函数。

通知事件回调调用 `invalidateQueries`：通知相关查询被标为需要更新，活跃查询按库行为重新获取。这段代码没有把 Socket 消息直接塞进列表，也没有在 Provider 中实现增量补偿。本阶段只需记住“实时信号告诉缓存重新读取”。

后半段实际实现为：

```tsx
void connection
  .then((nextDisconnect) => {
    if (disposed) {
      nextDisconnect();
      return;
    }
    disconnect = nextDisconnect;
  })
  .catch((error: unknown) => {
    if (!disposed) console.error('Notification realtime connection failed.', error);
  });

return () => {
  disposed = true;
  disconnect?.();
};
```

`disconnect?.()` 是可选调用：变量不是 null 时才执行。为何同时需要 `disposed` 和 `disconnect`？手算两条时间线就能看清：

| 时间线                   | 发生顺序                                                               | 哪一行真正清理                                |
| ------------------------ | ---------------------------------------------------------------------- | --------------------------------------------- |
| 先准备好连接，再离开     | Promise 完成 → 保存 disconnect → 卸载/状态变化触发 cleanup             | cleanup 的 `disconnect?.()`                   |
| 先离开，初始化后来才完成 | cleanup 发生时 disconnect 仍是 null → disposed=true → Promise 后来完成 | then 中发现 disposed，立即 `nextDisconnect()` |

如果只保留 cleanup 的 `disconnect?.()`，第二种情况下它执行时什么也拿不到；后面才得到的连接就可能继续存活。`disposed` 被 Promise 回调和 cleanup 共同读取，这就是闭包保存本轮 effect 局部状态的实际用途。

effect 依赖是 `[client, status]`。依赖变化时，React 会先清理上一轮再执行这一轮；组件卸载时也清理。这里不把 effect 回调声明为 `async`，因为 React 需要它直接返回清理函数，而不是一个 Promise。有关 setup/cleanup 的规则可对照 [React useEffect 文档](https://react.dev/reference/react/useEffect)。

对应 [RealtimeProvider.test.tsx](../src/app/providers/RealtimeProvider.test.tsx) 验证了晚到连接会断开、已建立连接卸载时会断开、匿名时不启动连接、挂载期间失败会报告、卸载后晚到失败被捕获且不再记录日志。测试通过可控制的 Promise 模拟时间顺序，重点是生命周期行为，不是证明真实网络一定可连通。

### 4.8 StrictMode：把开发检查和真实请求次数分开

根组件中的 `<StrictMode>` 没有用 `DEV ? ...` 条件包裹；它始终写在 JSX 中，但 React 的这些额外检查只在开发环境生效。它帮助发现不纯的渲染和漏掉清理的 effect，例如开发时额外检查渲染，并让 effect 经历额外的 setup/cleanup 检查周期。[React StrictMode 文档](https://react.dev/reference/react/StrictMode)。

结合刚读过的代码理解这个检查：Realtime 的 setup 安排连接，cleanup 必须能清掉这一轮工作，即使 Promise 在清理后才完成。若清理正确，再来一轮 setup 也不应留下多余的旧连接。

因此在开发环境看到多条日志或重复请求时，应先辨认日志属于渲染、effect、网络重试还是用户操作，再看清理和并发处理。不要把 StrictMode 简化为“所有代码固定执行两遍”或“生产必定只发一次请求”；实际网络次数还取决于挂载、重试、取消、缓存和应用代码。这里的额外检查也不会因为用户点一次按钮就自动把该点击事件执行两次。

同样不要把“根上有 StrictMode”当成“任何测试都正在验证 StrictMode”。刚才的 AuthBootstrap 和 RealtimeProvider 用例直接渲染被测组件，没有在这些测试代码中显式包这棵 ApplicationRoot。它们能证明各自断言覆盖的行为，不能自动扩大成整棵应用在所有开发生命周期下都已验证。

**题 1：把下面的子内容换成 `<DemoPage />`，它为什么能用 Query 和 Toast？是谁把它传到最里面？**

**答案：**嵌套内容成为 AppProviders 的 `children`；AppProviders 在 QueryClientProvider、ToastProvider、AuthBootstrap、RealtimeProvider 内放入它。Query/Toast 通过各自 Context 让后代读共享值；两个生命周期包装组件继续返回 children。因此 DemoPage 是这些 Provider 的后代。它不需要由每个包装组件再次手写一个 `showToast` Props。

**题 2：refresh 请求还没结束时，AuthBootstrap 会把 AppRouter 的渲染推迟到请求成功之后吗？是谁显示恢复提示？**

**答案：**不会。AuthBootstrap 直接返回 children，恢复通过 effect 异步进行。匹配到的守卫读取 bootstrapping 状态并返回加载提示，从而暂时替代受保护内容。不能把“具体页面正在等待认证”解释成“整个路由组件根本没有渲染”。

**题 3：以下四种现象，哪些由当前 Query 默认配置直接保证？**

- A：30 秒一到，自动请求所有接口。
- B：普通 Error 失败后一定重试两次。
- C：一次查询持续得到符合条件的 503 ApiError，最多追加两次重试。
- D：mutation 默认自动重试。

**答案：**只有 C 符合配置，且是在没有局部覆盖或取消等因素的一轮查询中。A 把新鲜时间误当轮询；B 漏看错误类型和状态条件；D 与 `mutations.retry: false` 相反。AuthBootstrap 的直接 API 调用也不自动套用这个 Query 重试配置。

**题 4：实时初始化还在等待 bootstrap 响应，组件已经卸载。如果删掉 then 里的 `if (disposed)`，只保留 cleanup，会出现什么缺口？**

## 五、从 URL 到页面：路由、守卫与布局

这一章解决一个具体问题：在地址栏输入 `/settings/profile` 后，项目如何决定显示哪个组件、是否先去登录、页面外面为什么有侧栏和顶栏？学完后，你应当能沿源码独立追踪任意一条现有路径，而不是只记住路由文件名。

本章依据当前项目源码讲解。路由定义在 [router.tsx](../src/app/router/router.tsx)，访问判断在 [guards.tsx](../src/app/router/guards.tsx)。路径工具的实际位置是 [shared/config/paths.ts](../src/shared/config/paths.ts)，项目没有要求你寻找另一个 `shared/router/paths.ts`。

### 5.1 先分清 URL、文件路径和组件

浏览器地址可以拆成几部分。例如：

```text
http://localhost:5173/search?q=React&tab=users#results
└────── origin ──────┘└path─┘└──── search ─────┘└ hash ┘
```

| 部分     | 示例                    | 本章中的用途                                                                 |
| -------- | ----------------------- | ---------------------------------------------------------------------------- |
| origin   | `http://localhost:5173` | 指向运行前端的站点。这里的端口只是开发地址示例。                             |
| pathname | `/search`               | 路由匹配主要根据它决定显示哪个页面。                                         |
| search   | `?q=React&tab=users`    | 同一页面接收的额外条件，例如关键词和分类。                                   |
| hash     | `#results`              | 片段标识；应用可用它定位页面区域。存在 hash 本身不保证页面一定实现滚动处理。 |

`/settings/profile` 是浏览器的页面地址；`src/pages/profile-edit/ProfileEditPage.tsx` 是磁盘上的源码文件；`ProfileEditPage` 是该文件导出的 React 组件。三者的名称可以不同，联系由路由表明确建立。

在传统多页网站里，一个地址可能对应服务器返回的一份 HTML。本项目则把 React 应用启动后，将多个地址映射到不同组件。点击应用内的 `Link` 时，路由通常更新地址与组件，无需重新加载整个 HTML 文档；直接粘贴地址或按刷新仍然会向服务器请求该地址，生产服务器需要能够把这些前端地址交回应用入口。路由表本身不会配置服务器。

### 5.2 路由对象是“匹配规则 + 显示内容”

打开 [router.tsx](../src/app/router/router.tsx)，先读结尾这段真实代码：

```tsx
export function AppRouter() {
  return <RouterProvider router={router} />;
}
```

`router` 是前面通过 `createBrowserRouter([...])` 创建的路由实例；`RouterProvider` 把它接入 React 界面。`router={router}` 表示把右边的 JavaScript 变量作为名叫 `router` 的属性传给组件。大写的 `RouterProvider` 是 React 组件，不是浏览器原生 HTML 标签。

再看创建实例的开头，下面保留真实字段并省略后续分支：

```tsx
const router = createBrowserRouter([
  {
    path: '/',
    errorElement: <RootErrorBoundary />,
    children: [
      { index: true, element: <Navigate to="/home" replace /> },
      // 后续还有 auth、onboarding、业务页面等分支
    ],
  },
]);
```

这里的 `[]` 是 JavaScript 数组，数组中的 `{...}` 是对象；它们描述路由规则，并不是 JSX 页面结构。与 JSX 中用于嵌入表达式的花括号相比，外观相同，语法位置和用途不同。

| 字段           | 含义                               | 在本项目里怎么读                                           |
| -------------- | ---------------------------------- | ---------------------------------------------------------- |
| `path`         | 地址匹配规则                       | `users/:handle` 匹配用户主页地址。                         |
| `element`      | 匹配时要渲染的 React 元素          | `<PublicLayout />`、守卫包裹的布局，或 `<Navigate />`。    |
| `children`     | 嵌套在当前路由下的路由规则数组     | `auth` 下的 `login` 组合成 `/auth/login`。                 |
| `index: true`  | 父级地址正好匹配时的默认子路由     | 打开 `/` 时选择其 index 子路由，随后转到 `/home`。         |
| `lazy`         | 按需取得该路由的组件等配置         | 动态导入 `ProfilePage`，避免所有页面都由路由文件静态导入。 |
| `errorElement` | 路由框架接收到错误时显示的替代界面 | 根路由统一使用 `RootErrorBoundary`。                       |

根路由设置了错误界面，但没有自己的 `element`。在这种结构下，匹配的子分支可以直接呈现，不需要专门增加一个“根页面”组件。

`index` 不是文件夹里的 `index.ts`，也不是数组下标。它是一种路由规则：只匹配父路由本身的地址，不再增加一段路径。例如 `/onboarding` 的 index 子路由写的是 `<Navigate to="interests" replace />`，其相对目标对应 `/onboarding/interests`。不过当前父级守卫还会依据服务端引导状态先决定去哪个步骤，不能把 index 跳转理解为所有用户都会强制重新从第一步开始。

### 5.3 `children` 定义嵌套关系，`Outlet` 指定显示位置

认证路由的真实写法如下，这里只摘取登录分支：

```tsx
{
  path: 'auth',
  element: <PublicLayout />,
  children: [
    {
      path: 'login',
      lazy: async () => ({
        Component: (await import('@/pages/auth/LoginPage')).LoginPage,
      }),
    },
  ],
},
```

父路径 `auth` 加上子路径 `login`，得到 `/auth/login`。地址匹配后，父布局和子页面都参与显示。子页面具体放在哪里，要到 [PublicLayout.tsx](../src/app/layouts/PublicLayout.tsx) 找：

```tsx
<section className={styles.panel}>
  <Outlet />
</section>
```

`section` 是 HTML 区域标签；`className` 给它设置 CSS 类。`Outlet` 是 React Router 提供的组件，含义是“在这里呈现当前匹配的子路由”。访问登录页时这里呈现 `LoginPage`，注册页时呈现 `RegisterPage`，周围的品牌区仍由同一个布局负责。

可以把实际关系画成下面的树：

```text
URL /auth/login
└─ auth 路由
   └─ PublicLayout
      ├─ 品牌介绍区
      └─ 表单面板 section
         └─ Outlet
            └─ LoginPage
```

假如一个父路由有自己的 `element`，而该组件既不渲染 `Outlet`，也不通过其他方式呈现子路由，那么“地址匹配成功”并不等于“子页面已经放进父页面”。读嵌套路由时，要把路由文件和布局里的插入位置连起来看。

这里还有两种容易混淆的 `children`：

```tsx
<RequireCompletedOnboarding>
  <AppShellLayout />
</RequireCompletedOnboarding>
```

上面是组件的 `children` 属性：`AppShellLayout` 作为内容传给守卫。它与路由对象里的 `children: [...]` 数组不是同一个东西。守卫决定要不要返回传入的布局；布局中的 `Outlet` 再呈现路由数组匹配出的业务页面。

### 5.4 没有 `path` 的分支为什么也能工作

业务页面的父路由实际没有 `path`。下面也是源码节选：

```tsx
{
  element: (
    <RequireCompletedOnboarding>
      <AppShellLayout />
    </RequireCompletedOnboarding>
  ),
  children: [
    {
      path: 'users/:handle',
      lazy: async () => ({
        Component: (await import('@/pages/profile/ProfilePage')).ProfilePage,
      }),
    },
    // 同组还有 home、explore、search、settings/profile 等
  ],
},
```

这种无路径路由常称为 **pathless route**。它提供共享的渲染层级和守卫，不给 URL 增加路径片段。因此用户主页仍是 `/users/someone`，不会变成 `/app/users/someone`。

要注意，**URL 看起来有父子层级，不代表代码真的使用了嵌套路由**。本项目的 `settings` 与 `settings/profile` 是同一个业务 `children` 数组里的两个路由对象。访问 `/settings/profile` 时匹配的是资料编辑页，不会先显示 `SettingsOverviewPage`，再把编辑页嵌入它的 `Outlet`。

同理，`users/:handle`、`users/:handle/followers`、`users/:handle/following` 在此处也分别声明为同级规则。后两者共享 `loadFollowListPage` 加载函数，不代表它们由 `ProfilePage` 内部渲染。

### 5.5 `lazy` 延迟加载什么，什么时候会运行守卫

用户主页路由的这一行值得拆开读：

```tsx
Component: (await import('@/pages/profile/ProfilePage')).ProfilePage,
```

1. `import('...')` 是动态导入，返回 Promise，最终取得该模块的导出对象。
2. `await` 等待动态导入完成，所以外层函数写成 `async`。
3. `(...).ProfilePage` 从模块导出中取出名为 `ProfilePage` 的组件函数。
4. `{ Component: ... }` 把组件交给路由框架。这里返回的是组件函数，不是提前调用 `ProfilePage()`。

项目的页面采用命名导出，所以这里读取 `.ProfilePage`；如果把它误写成 `.default`，就与当前页面的导出方式不一致。

`lazy` 在这里延迟的是路由组件代码。页面内部的用户资料、帖子列表等请求，仍由 `useQuery` 或领域 Hook 发起；“模块加载完毕”和“业务数据加载完毕”是不同阶段。页面自己的 skeleton 也主要反映数据请求状态，不自动等同于路由代码下载进度。

还要区分学习时的逻辑顺序与浏览器的网络时序：你可以按“匹配路由 → 判断访问条件 → 布局 → 页面”理解显示结果，但 React Router 为解析匹配分支可能先加载对应的 lazy 模块，再渲染组件守卫。**这里的守卫控制受保护内容能否呈现，不能保证匿名用户绝不会下载到该页面的 JavaScript。** API 的身份和权限校验仍需由服务端负责。

### 5.6 路径参数、查询参数与路径生成工具

先看动态路径参数。路由中的 `:handle` 是变量名，不是要求地址栏真的包含冒号。[ProfilePage.tsx](../src/pages/profile/ProfilePage.tsx) 用下面这行取值：

```tsx
const { handle = '' } = useParams();
```

访问 `/users/someone` 时，匹配到的 `handle` 就是字符串 `someone`。花括号表示解构取出 `handle`；`= ''` 是缺失时的默认值。随后页面实际用它查询资料：

```tsx
const profileKey = userKeys.profile(handle);
const profile = useQuery({
  queryKey: profileKey,
  queryFn: ({ signal }) => usersApi.profile(handle, signal),
  enabled: Boolean(handle),
});
```

在第二阶段先理解三点即可：`queryKey` 区分不同用户的缓存，`queryFn` 是取得资料的函数，`enabled` 防止空 Handle 时发起这个查询。参数把“同一个组件”变成“显示不同用户的组件”。

其他现有例子：

| 规则                                        | 示例地址                                    | 能取得的参数                                                      |
| ------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------- |
| `posts/:postId`                             | `/posts/post-123`                           | `postId = 'post-123'`                                             |
| `posts/:postId/media/:mediaIndex`           | `/posts/post-123/media/2`                   | `postId = 'post-123'`、`mediaIndex = '2'`；数字仍需页面自己解析。 |
| `compose/:draftId?`                         | `/compose` 或 `/compose/draft-123`          | `?` 在路径规则里表示 draftId 可选。                               |
| `bookmarks/:collectionId?`                  | `/bookmarks` 或 `/bookmarks/collection-123` | collectionId 可选。                                               |
| `communities/:communityId/manage/:section?` | `/communities/c1/manage/members`            | communityId 和可选 section。                                      |

查询参数使用另外一套读取方式。[SearchPage.tsx](../src/pages/search/SearchPage.tsx) 的真实片段是：

```tsx
const [params, setParams] = useSearchParams();
const query = params.get('q') || '人工智能';
const tab = (params.get('tab') || 'posts') as SearchTab;
```

`/search?q=React&tab=users` 仍匹配 `path: 'search'`，不是去匹配一个包含 `?q=` 的路由。`useSearchParams` 返回读取参数的对象和修改参数的函数；`get('q')` 得到关键词，`get('tab')` 得到分类。`as SearchTab` 是给 TypeScript 的类型断言，**不会在运行时自动校验 URL 里写的值**。

路径规则里的 `:draftId?` 和真实 URL 里的 `?q=React` 虽然都出现问号，用途不同：前者是路由配置中的“可选段”，后者是地址中的“查询字符串起点”。

[paths.ts](../src/shared/config/paths.ts) 集中生成跳转地址，避免每个页面自己拼字符串。两个真实片段如下：

```ts
const profilePath = (handle: string) => `/users/${encodePathSegment(handle)}`;
```

```ts
searchResults: (query: string) => `${SEARCH_PATH}?q=${encodeURIComponent(query)}`,
```

第一段会被导出为 `paths.profile`；`encodePathSegment` 内部也使用 `encodeURIComponent`。它对路径段或查询值中的特殊字符编码，避免输入里的 `&`、`?`、空格等被误认成 URL 的结构。它不是加密，也不是权限校验。

此处要记住两个不同职责：`paths.profile('someone')` **生成目标地址**；`router.tsx` 的 `users/:handle` **识别目标地址**。只往 `paths` 添加一个字符串，并不会自动创建页面路由。相反，即使路由已经存在，也可以直接输入地址访问，不需要先有一个导航按钮。

### 5.7 守卫是一种会返回不同界面的组件

[guards.tsx](../src/app/router/guards.tsx) 里最短的守卫如下：

```tsx
export function RequireAuth({ children }: { children: ReactNode }) {
  const status = useAuthStore((state) => state.status);
  if (status === 'bootstrapping') return <Bootstrapping />;
  if (status === 'anonymous') return <LoginRedirect />;
  return children;
}
```

逐句读：

1. 函数接收 `children`，类型 `ReactNode` 表示可作为 React 内容的值。
2. 从认证 store 读取 `status`，并订阅它的变化。状态更新后组件会重新判断。
3. `bootstrapping` 意味着会话仍在恢复，先显示“正在恢复会话”的 Spinner。
4. `anonymous` 表示已确认没有登录，返回登录重定向组件。
5. 其余正常认证状态返回 `children`，也就是调用它时传入的内容。

这个守卫本身不请求登录接口，也不负责恢复 token。认证 store 初始状态是 `bootstrapping`；[AuthBootstrap.tsx](../src/app/providers/AuthBootstrap.tsx) 发起会话恢复并更新状态，守卫响应这个结果。把“尚未知道是否登录”单独表示出来，可以避免刷新页面时一瞬间把已有会话用户误送去登录页。

三个守卫的判断可以用一张表看清楚。以下“返回内容”指返回传入的 `children`：

| 当前情况           | `RequireAuth`                 | `RequireCompletedOnboarding`                       | `RequireOnboarding`                      |
| ------------------ | ----------------------------- | -------------------------------------------------- | ---------------------------------------- |
| 会话恢复中         | 恢复会话加载界面              | 恢复会话加载界面                                   | 恢复会话加载界面                         |
| 未登录             | 去 `/auth/login` 并记住原目标 | 同左                                               | 同左                                     |
| 已登录，已完成引导 | 返回内容                      | 返回内容                                           | 去 `/home`                               |
| 已登录，未完成引导 | 返回内容；它不检查引导        | 去服务端状态对应的引导路径；映射为空时回退 `/home` | 已在正确步骤则返回内容，否则转到正确步骤 |

`RequireCompletedOnboarding` 中的关键源码是：

```tsx
if (!onboardingCompleted) {
  return <Navigate to={onboardingPathForStatus(onboardingStatus) ?? '/home'} replace />;
}
return children;
```

`!` 表示逻辑取反，`??` 表示左侧为 `null` 或 `undefined` 时使用右侧值。布尔字段 `onboardingCompleted` 和具体步骤 `onboardingStatus` 都来自会话状态；读代码时应把它们一起看，不能只根据某个状态名推断所有分支。

引导守卫的额外检查是：

```tsx
const expectedPath = onboardingPathForStatus(onboardingStatus);
if (expectedPath && location.pathname !== expectedPath) {
  return <Navigate to={expectedPath} replace />;
}
return children;
```

它比较的是 `pathname`，因此不会因为查询参数不同就被判定为另一引导步骤。它也并非只阻止“跳到后面的步骤”：只要当前 pathname 不是期望步骤，向前或向后手改地址都会被纠正。若 expectedPath 为空，则此项检查不发起跳转。

当前引导映射在 [onboardingRoute.ts](../src/domains/auth/model/onboardingRoute.ts)：

| `onboardingStatus`                | 返回路径                  | 解释                                                                 |
| --------------------------------- | ------------------------- | -------------------------------------------------------------------- |
| `PENDING_HANDLE`                  | `/onboarding/interests`   | 当前实现也回到第一个已实现的兴趣步骤；不要自行推断成 Google 补全页。 |
| `PENDING_INTERESTS`               | `/onboarding/interests`   | 选择兴趣。                                                           |
| `PENDING_RECOMMENDED_USERS`       | `/onboarding/follow`      | 推荐关注。                                                           |
| `PENDING_RECOMMENDED_COMMUNITIES` | `/onboarding/communities` | 加入社群。                                                           |
| `PENDING_COMPLETE`                | `/onboarding/communities` | 继续最后一步。                                                       |
| `COMPLETED`、`SKIPPED`            | `null`                    | 不再提供下一引导页面。                                               |
| `null` 或落入 default             | `/onboarding/interests`   | 回退到第一个已实现步骤。                                             |

状态应由正常会话流程保持一致。如果手动把 store 改成 `onboardingCompleted: false` 同时步骤却是 `COMPLETED`，就可能走到回退分支。这不是学习时应假设的正常组合，也不代表守卫会自动修复这两个字段。

### 5.8 `Navigate`、`replace` 和 `state` 如何配合登录返回

未登录时的重定向组件源码是：

```tsx
function LoginRedirect() {
  const location = useLocation();
  return (
    <Navigate to="/auth/login" replace state={{ from: location.pathname + location.search }} />
  );
}
```

`Navigate` 是一个用于导航的 React 组件，不是登录页 HTML。它渲染时让路由切换到 `to` 指定的位置。

`replace` 控制浏览历史：用登录地址替换当前这条历史记录，而非再追加一条。假设历史为“首页 → 想访问的设置页”，守卫把设置页替换为登录页，可减少后退时反复回到受保护地址、再被送回登录的循环。它不会删除用户所有历史，也不是“禁止浏览器后退”。

`state` 是这次导航携带的额外数据，不会显示为地址栏查询参数。这里的对象把原目标保存在 `from`。例如匿名打开：

```text
/search?q=React&tab=users
```

登录页收到的 `location.state` 可包含：

```ts
{
  from: '/search?q=React&tab=users';
}
```

当前实现保存 pathname 与 search，没有保存 hash。`state` 不属于复制 URL 时附带的信息，也不是可以跨设备依赖的存储，所以登录页仍然需要回退地址。

[LoginPage.tsx](../src/pages/auth/LoginPage.tsx) 登录成功后的真实代码：

```tsx
const from = (location.state as { from?: string } | null)?.from || '/home';
const destination = session.onboardingCompleted
  ? from
  : (onboardingPathForStatus(session.onboardingStatus) ?? from);
void navigate(destination, { replace: true });
```

第一行使用可选链 `?.` 安全读取 `from`，没有就使用 `/home`。后面的三元表达式 `条件 ? A : B` 表示：引导完成则回原目标，否则优先进入需要继续的引导步骤。`navigate(...)` 是事件处理函数里主动导航的方式，`Navigate` 则是根据渲染状态声明导航的组件，两种写法在本项目都存在。

`void` 用在这里表示忽略该表达式的返回值；它不表示“吞掉所有异常”。另外，普通登录已完成引导时可以恢复 `from`，并不等于所有 Google 补全/引导完成分支也都会保存并恢复最初目标：那些页面有各自的后续导航逻辑。

### 5.9 三种 Layout：固定区域与变化区域

`Layout` 是项目的组件命名，不是一个特殊 HTML 标签。布局用 `div/main/section/header` 等 HTML 结构配合 CSS，组织共用区域；`Outlet` 负责把当前路由页面放进空位。

| 布局                                                        | 被哪组路由使用                             | 固定区域                                | `Outlet` 中变化的内容                           | 守卫在哪一层                                                                 |
| ----------------------------------------------------------- | ------------------------------------------ | --------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| [PublicLayout](../src/app/layouts/PublicLayout.tsx)         | `/auth/...`                                | 品牌介绍、功能介绍、右侧表单面板        | 登录、注册、密码恢复、邮箱验证、Google 补全页面 | 这个路由分支没有使用本章的三种守卫。布局名不表示所有“公开内容页面”都在这里。 |
| [OnboardingLayout](../src/app/layouts/OnboardingLayout.tsx) | `/onboarding/...`                          | 品牌、当前第几步、三步进度、“稍后完成”  | 兴趣、推荐关注、推荐社群                        | 路由的 element 外面包着 `RequireOnboarding`。                                |
| [AppShellLayout](../src/app/layouts/AppShellLayout.tsx)     | 首页、探索、搜索、用户、内容、设置等业务组 | `Sidebar`、`Topbar`、`MobileNavigation` | 匹配的业务页面                                  | 路由的 element 外面包着 `RequireCompletedOnboarding`。                       |

[AppShellLayout.tsx](../src/app/layouts/AppShellLayout.tsx) 很短，可以整段精读：

```tsx
export function AppShellLayout() {
  return (
    <div className={styles.shell}>
      <Sidebar />
      <div className={styles.workspace}>
        <Topbar />
        <div className={styles.content}>
          <Outlet />
        </div>
      </div>
      <MobileNavigation />
    </div>
  );
}
```

从外往里看：最外层 shell 放左侧导航与工作区；工作区先放顶栏，再放 content；content 的 `Outlet` 放具体页面；移动导航作为另一个组件挂在外层。把 `Outlet` 换成当前页面名字，就是这个地址对应的组件结构。

布局与 CSS 的联系可以从 [AppShellLayout.module.css](../src/app/layouts/AppShellLayout.module.css) 看一个真实片段：

```css
.shell {
  width: min(1376px, calc(100% - 64px));
  min-height: 100vh;
  margin: 0 auto;
  display: grid;
  grid-template-columns: var(--sidebar-width) minmax(0, 1fr);
  gap: var(--app-gap);
  padding: 24px 0;
}
```

`display: grid` 开启网格布局；`grid-template-columns` 把主要内容排成侧栏与剩余工作区两列；`var(...)` 读取项目定义的 CSS 变量；`minmax(0, 1fr)` 让第二列使用剩余空间并允许收缩；`100vh` 表示至少一个浏览器视口高度。`margin: 0 auto` 让限宽内容水平居中。理解这些，才能把 JSX 的结构和浏览器中的两列外观对应起来。

该 CSS 在 1180px 以下收窄侧栏，在 760px 以下把 shell 改成块布局并留底部空间。PublicLayout 在 900px 以下隐藏品牌栏；OnboardingLayout 在 760px 以下调整头部与边距。窗口尺寸改变的是布局表现，不会使路由自动换成另一个页面。

`OnboardingLayout` 还包含少量业务行为：“稍后完成”先调用 `onboardingApi.skip()`，成功更新 auth store 后才 replace 到首页；失败显示 Toast 并留在引导。不能把这个按钮解释成单纯导航链接。它的步骤高亮使用当前 pathname，与守卫使用服务端步骤决定允许位置相互配合。

最后区分一个同样叫布局的组件：[shared/ui/layout/PageLayout.tsx](../src/shared/ui/layout/PageLayout.tsx)。它接收普通 `children` 和可选 `aside`，组织某个业务页面内部的主栏/右栏；它没有 `Outlet`。因此一页可以同时拥有外层路由布局 `AppShellLayout` 和内层页面布局 `PageLayout`，两者负责不同范围。

### 5.10 完整追踪一：输入 `/users/someone`

这里的 `someone` 是用于讲解的 Handle 占位，不保证真实用户存在。先假设会话最终恢复为“已登录且引导完成”。

1. 应用入口渲染 `ApplicationRoot`，其中 `AppProviders` 包裹 `AppRouter`；`AppRouter` 返回 `RouterProvider`。前面的启动流程准备好了这一层后，路由才把当前位置变成页面。
2. `/users/someone` 匹配根 `/` 下业务无路径分支的 `users/:handle`。`auth` 与 `onboarding` 都不是此次的父路径。
3. 路由通过 lazy 导入 `src/pages/profile/ProfilePage.tsx` 并取得 `ProfilePage`；不要把这一项当作已经请求了用户资料。
4. `RequireCompletedOnboarding` 检查会话和引导状态。如果仍在恢复，当前显示“正在恢复会话”；满足条件后返回 `AppShellLayout`。
5. `AppShellLayout` 显示侧栏、顶栏等固定部分，在 content 的 `Outlet` 呈现 `ProfilePage`。
6. `ProfilePage` 调用 `useParams()` 取得 `handle = 'someone'`，用 `usersApi.profile(handle, signal)` 读取个人资料，并用 `postsApi.byAuthor(...)` 查询其帖子。
7. 组件根据各查询状态显示骨架、错误重试或用户资料与帖子；它再用 `PageLayout` 组织资料主区域和关系侧栏。不存在的用户是业务查询结果的问题，不是路由一定找不到。

最终的逻辑组件树是：

```text
RouterProvider
└─ 匹配根路由下的业务分支
   └─ RequireCompletedOnboarding
      └─ AppShellLayout
         ├─ Sidebar
         ├─ 工作区
         │  ├─ Topbar
         │  └─ Outlet → ProfilePage
         │     └─ PageLayout → 用户资料、帖子、关系侧栏
         └─ MobileNavigation
```

改变前提，结果会改变：未登录时不会返回 AppShellLayout，而是去登录并记住 `/users/someone`；已登录但步骤为 `PENDING_RECOMMENDED_USERS` 时会先去 `/onboarding/follow`。所以页面中即使有“登录后查看关系”的文案，也不能据此认定当前路由允许匿名进入。

### 5.11 完整追踪二：输入 `/settings/profile`

这次先从“未登录”开始，便于观察前面的机制如何连接：

1. `/settings/profile` 匹配业务无路径分支中的 `path: 'settings/profile'`。路由对应的 lazy 导入是 `src/pages/profile-edit/ProfileEditPage.tsx`。
2. 守卫在会话恢复完成、得到 `anonymous` 后返回 `LoginRedirect`。
3. 地址被 replace 为 `/auth/login`，导航 state 保存 `{ from: '/settings/profile' }`。
4. 现在匹配的是 `auth → login`，显示 PublicLayout 的品牌区及 Outlet 中的 LoginPage；AppShellLayout 不属于这个匹配分支。
5. 用户完成普通密码/验证码登录。如果返回会话的 `onboardingCompleted` 为 true，LoginPage 读取 from，再 replace 回 `/settings/profile`；若为 false，先去服务端指定的引导步骤。
6. 假设引导已经完成，守卫放行，AppShellLayout 的 Outlet 开始渲染 ProfileEditPage。
7. 这个地址没有 `:handle`。ProfileEditPage 查询 `usersApi.getOwnEditableProfile(signal)`，获取当前登录账号自己的可编辑资料；它不从 URL 猜测要编辑哪个用户。
8. 正在查询时显示“正在加载个人资料”，失败时显示页面内的错误与重试，成功后渲染内部 `ProfileEditEditor` 表单。表单使用 PageLayout 与 Card，并处理头像、封面和文本字段。

这条路径尤其能纠正两个误会：URL 包含 `settings` 不代表一定渲染 SettingsOverviewPage；资料编辑页虽然属于设置地址，当前源码也没有使用 `pages/settings/ui/SettingsPage` 的设置导航容器。是否出现某个布局，要看实际 element 和组件返回值。

把两条路径并排比较：

| 问题          | `/users/someone`                            | `/settings/profile`                      |
| ------------- | ------------------------------------------- | ---------------------------------------- |
| 路由规则      | `users/:handle`                             | `settings/profile`                       |
| 参数          | 有 `handle`                                 | 无路径参数                               |
| 页面          | ProfilePage                                 | ProfileEditPage                          |
| 外层守卫/布局 | RequireCompletedOnboarding / AppShellLayout | 同左                                     |
| 主要身份来源  | URL 中指定用户                              | 当前登录会话                             |
| 主要查询      | `usersApi.profile(handle, signal)`          | `usersApi.getOwnEditableProfile(signal)` |
| 页面内布局    | PageLayout                                  | PageLayout                               |

### 5.12 根路由的错误出口与特殊路由

根路由注册了 `errorElement: <RootErrorBoundary />`。匹配分支中的路由加载或渲染错误，可以沿路由树交给这个错误界面。它与页面自己显示的请求失败提示不同；完整源码、捕获范围和三类错误的比较见[第六节](#stage2-errors)。

另外，`/__dev/states` 是可以正常访问的系统状态展示路由。其实际规则是 `RequireAuth` 包裹一个 Outlet，index 子路由加载 SystemStatesDevPage。**当前声明没有 `import.meta.env.DEV` 条件，也没有额外管理员判断；名字里的 `__dev` 不会自动让它仅在开发环境可用。** 它也没有要求完成 onboarding，和常规业务分支不同。

### 5.14 自测：先写答案，再对照解析

**题 1：** 匿名用户输入 `/users/someone?tab=media`，为什么不会直接显示 PublicLayout 中的用户主页？登录页能收到什么 from？

**答案：** 该路径匹配业务无路径分支的 `users/:handle`，该分支使用 RequireCompletedOnboarding。匿名状态使它转到 `/auth/login`，state 的 from 是 `/users/someone?tab=media`。此时 PublicLayout 装配的是 LoginPage。查询参数被记住不代表 ProfilePage 一定实现了 URL tab 功能；当前 ProfilePage 的帖子/媒体 tab 是组件内状态。

**题 2：** 已登录但引导状态是 `PENDING_RECOMMENDED_COMMUNITIES`，手动访问 `/onboarding/interests` 会发生什么？

**答案：** RequireOnboarding 把 expectedPath 算为 `/onboarding/communities`，发现当前 pathname 不一致后 replace 到那里。守卫使当前位置与服务端步骤一致，不只是禁止往后跳。

**题 3：** 为什么 `/settings/profile` 没有先渲染 SettingsOverviewPage？

**答案：** `settings` 和 `settings/profile` 是路由配置里的同级规则，地址前缀相同不会自动建立组件嵌套。它们共同的父级是业务无路径路由，继承的外壳是 AppShellLayout。

**题 4：** 将 AppShellLayout 中的 Outlet 删除，为什么地址还可能显示 `/users/someone`，但看不到用户页？

**答案：** 路由仍能匹配这个地址，但父布局没有给匹配的子页面提供渲染位置。地址匹配与界面插入是两个相互配合的环节。

**题 5：** `/compose/draft-123` 的 draftId 和 `/compose?community=c1` 的 community 应分别如何读取？

**答案：** draftId 来自路由 `compose/:draftId?` 的路径参数，通过 `useParams` 读取；community 属于查询字符串，通过 `useSearchParams` 等查询解析方式读取。可选 draftId 不意味着查询参数会自动成为路径参数。

**题 6：** 根路由有 errorElement，是否可以删掉 ProfileEditPage 中的请求错误状态和重试按钮？

**答案：** 不可以据此删除。该请求由 React Query 管理，失败在页面 `isError` 分支显示；它不是自动抛给路由框架的 loader 错误。根边界与局部错误反馈服务不同的失败情况。

**题 7：** 只在 paths 对象增加 `help: '/help'`，再写一个指向它的 Link，帮助页会自动存在吗？

**答案：** 不会。路径工具只是生成地址，还要提供页面组件并在 router.tsx 配置对应匹配规则，否则通常会落到 `*` 的 NotFoundPage。

**题 8：** 已登录但未完成 onboarding 的用户能否访问 `/__dev/states`？构建生产版本是否必然删除这个入口？

**答案：** 按当前声明，可以通过该路由的 RequireAuth，因为它不检查 onboardingCompleted；源码也未用 DEV 条件声明该路由，因此不能保证生产版本删除它。

完成本章的可操作验收是：不运行项目，先为一个地址写出“匹配规则 → 守卫结果 → 布局 → Outlet 中的页面 → 参数来源”；然后逐个打开本文链接，对照源码确认。若看到的界面与预测不同，优先检查会话状态、引导状态和页面自己的请求分支，而不是只搜索 URL 对应的文件夹。

## 六、错误出现在哪一层，就从哪一层理解

### 6.1 先区分三种容易混在一起的失败

| 场景                                             | 本项目的处理位置                                    | 你可能看到什么                     |
| ------------------------------------------------ | --------------------------------------------------- | ---------------------------------- |
| 动态加载挂载模块失败，或挂载函数等待的初始化失败 | bootstrapApplication 的 catch 调用 bootstrapFailure | “应用暂时无法启动”原生 DOM 卡片    |
| 路由系统内的页面模块加载失败、路由渲染抛错等     | 根路由的 errorElement：RootErrorBoundary            | “页面加载失败”等路由错误页         |
| 页面把接口失败作为数据状态处理                   | 页面自己的 isError 分支，或操作 catch + Toast       | 页面中的失败提示、重试按钮或 Toast |

第三行不是另一个统一文件名。不同页面可以选择自己的呈现方式；本文用 HomePage 的真实代码说明。

另外，根元素缺失是单独一条路径：源码只记录 missing-root，并不渲染 bootstrapFailure。

### 6.2 为什么启动失败页使用原生 DOM

[源码：bootstrapFailure.ts](../src/app/bootstrapFailure.ts) 负责在 React 应用模块加载失败等情况下提供可见反馈。此时不应该把这张提示页的显示建立在“React 一定已经可用”上，所以它使用浏览器 DOM API。

可以把该函数的行为拆为：

```text
取得 root 所属的 document
  → 创建 main、section、文本、按钮
  → 设置属性与点击处理器
  → 组装成树
  → 替换 root 中的旧内容
  → 把键盘焦点移到重试按钮
```

这份文件是整个项目里练习“原生 HTML 如何由 JavaScript 创建”的好入口。

### 6.3 创建元素和放入页面，是两步

真实片段：

```ts
const ownerDocument = root.ownerDocument;
const page = ownerDocument.createElement('main');
page.dataset.appBootstrapFailure = '';
```

逐行理解：

- root.ownerDocument 是 root 所属的文档对象。
- createElement('main') 创建一个 main 元素，此时只是创建出来，还没有放进可见的 DOM 树。
- dataset.appBootstrapFailure 设置一个自定义数据属性。

第二、三行的结果可以用 HTML 表示为：

```html
<main data-app-bootstrap-failure=""></main>
```

这里没有 XML 的特殊含义，它是普通 HTML 元素：

| 部分                       | 含义                             |
| -------------------------- | -------------------------------- |
| main                       | 表示页面主要内容区域的 HTML 标签 |
| data-app-bootstrap-failure | 自定义属性名                     |
| =""                        | 属性值为空字符串                 |
| </main>                    | 结束标签                         |

dataset 会把 JavaScript 里的驼峰名称转换成 HTML 的短横线形式：`appBootstrapFailure` 对应 `data-app-bootstrap-failure`。相关规则见 [MDN：使用 data 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/Use_data_attributes)。

空字符串不意味着“没有属性”。这里刻意用属性是否存在，标记“这是一张启动失败页”。它不是浏览器内置的 disabled 一类布尔属性，也不会自己触发样式或某种错误行为。

选择 root.ownerDocument 而不是直接写死全局 document，让创建出来的元素与挂载点属于同一文档。对应的测试确实创建了一个独立文档来验证这一点。

### 6.4 原生元素的属性、文本和无障碍关系

真实代码：

```ts
const card = ownerDocument.createElement('section');
card.setAttribute('role', 'alert');
card.setAttribute('aria-labelledby', 'app-bootstrap-failure-title');
card.setAttribute('aria-describedby', 'app-bootstrap-failure-description');

const title = ownerDocument.createElement('h1');
title.id = 'app-bootstrap-failure-title';
title.textContent = '应用暂时无法启动';
```

`setAttribute(属性名, 属性值)` 设置 HTML 属性。`title.id = ...` 也是给元素设置 id。`textContent` 设置文本内容，不把文本当成 HTML 标签解析。

三个属性是为辅助技术提供语义：

- role="alert"：把这块内容标记为需要注意的提示区域。
- aria-labelledby：通过 id 指向作为该区域标题的元素。
- aria-describedby：通过 id 指向说明文字。

它们不会替你画边框或改背景色，也不是 JavaScript 的点击事件。样式仍然由 CSS 负责。

### 6.5 它没有 class，为什么仍然有样式

因为 [global.css](../src/app/styles/global.css) 使用了属性选择器：

```css
[data-app-bootstrap-failure] {
  display: grid;
  min-height: 100vh;
  padding: 32px;
  place-items: center;
  background: var(--gradient-brand-soft);
}
```

方括号的意思是“选中具有这个属性的元素”，所以前面的 main 会被选中。

几个不同选择器对照：

| CSS 写法                                 | 选中什么                                   |
| ---------------------------------------- | ------------------------------------------ |
| `main`                                   | 所有 main 标签                             |
| `.page`                                  | class 中包含 page 的元素，属于类选择器     |
| `#root`                                  | id 为 root 的元素                          |
| `[data-app-bootstrap-failure]`           | 具有指定属性的元素，不要求某个具体值       |
| `[data-app-bootstrap-failure=""]`        | 该属性的值恰好为空字符串的元素             |
| `[data-app-bootstrap-failure] > section` | 标记元素的直接 section 子元素              |
| `[data-app-bootstrap-failure] button`    | 标记元素内部任意层级的 button 后代         |
| `button:focus-visible`                   | 满足 focus-visible 状态的 button，使用伪类 |

以点开头的 `.page` 是**类选择器**。尽管 class 也是 HTML 属性，CSS 分类里也不因此把点号写法叫作属性选择器。

样式中的：

- min-height: 100vh：最小高度按视口高度计算。
- display: grid + place-items: center：用网格布局让直接内容居中。
- var(--gradient-brand-soft)：读取项目的 CSS 自定义属性；定义可追到 [tokens.css](../src/app/styles/tokens.css)。

加载链是：

```text
main.ts 导入 global.css
  → global.css 导入 tokens/reset/typography
  → global.css 中的属性选择器匹配启动失败 DOM
  → 浏览器应用样式
```

data 属性只充当标记；CSS 规则负责外观；JavaScript 负责创建元素与交互，这三者在这里配合。

### 6.6 重试按钮什么时候才会刷新

真实代码：

```ts
retryButton.type = 'button';
retryButton.textContent = '重新加载';
retryButton.addEventListener('click', onRetry, { once: true });

card.append(eyebrow, title, description, retryButton);
page.append(card);
root.replaceChildren(page);
retryButton.focus();
```

按顺序看：

1. type='button' 明确它是普通按钮。
2. 设置按钮文字。
3. 注册 click 监听器，传入的是 onRetry 函数，而不是 onRetry() 的执行结果。
4. append 把各节点放进父节点，形成 main → section → 文本/按钮的树。
5. replaceChildren 清除 root 原来的子内容，并放入新树，root 这个元素本身仍然保留。
6. focus 将键盘焦点移到按钮，便于用户直接操作。

`{ once: true }` 表示该监听器调用一次后移除。它不等于给按钮设置 disabled，不会自动显示加载状态，也不代表以后再调用这个渲染函数时不能注册新的监听器。

onRetry 是从 main.ts 一路传下来的：

```text
main.ts 创建刷新回调
  → 传给 bootstrapApplication
  → 出错后转交 renderBootstrapFailure
  → 注册到 click
  → 用户点击
  → window.location.reload()
```

### 6.7 路由错误页：必须已经进入 React 路由这套机制

[源码：RootErrorBoundary.tsx](../src/app/error/RootErrorBoundary.tsx) 的关键逻辑：

```tsx
const error = useRouteError();
const status = isRouteErrorResponse(error) ? error.status : 500;
const title = isRouteErrorResponse(error)
  ? `${error.status} ${error.statusText || '请求失败'}`
  : '页面加载失败';
const message = getErrorMessage(error, '系统暂时无法完成请求，请稍后重试。');
```

它使用 React Router 提供的错误信息：

- 如果是路由识别的错误响应，取其状态码和状态文字。
- 否则使用代码中设置的展示值 500 和通用标题。
- 再生成适合显示的说明文字。当前 getErrorMessage 对 Error 实例提取非空 message，其余情况使用兜底说明。

因此页面看到 ERROR · 500，不足以证明后端真的返回了 HTTP 500；这里的 500 也可能只是普通 JavaScript 异常的默认展示值。

它在 [router.tsx](../src/app/router/router.tsx) 的根路由上通过 `errorElement: <RootErrorBoundary />` 注册。子路由错误可以向上交给该边界，但 Provider 在 RouterProvider 外部的错误不因此获得同样覆盖。当前只在根路由声明 errorElement，发生相应错误时会显示根级替代界面，不能假定原有侧栏和顶栏仍然保留。

错误页中的“重新加载”刷新整个文档，“返回首页”使用 Link 导航到 /home，仍然会经过首页正常的守卫。React Router 也支持捕获路由 loader/action 的错误，不过当前 router.tsx 没有配置 loader/action；项目业务数据请求主要在组件/领域 Hook 中发起。

还要区分“页面运行期间”与“边界能捕获”：

| 故障                                     | 该从哪里理解                                                 |
| ---------------------------------------- | ------------------------------------------------------------ |
| 路由 lazy 导入页面模块失败               | 属于路由加载错误，可进入路由错误处理                         |
| 路由下的组件在渲染时抛错                 | 可由相应路由错误边界处理                                     |
| 用户点击后，事件处理器里抛错             | 不会仅因发生在该页面就自动显示 errorElement                  |
| 事件里发起的 Promise 拒绝，未自行处理    | 不能指望路由边界自动兜底                                     |
| 页面请求失败，被 Query 保存为 error 状态 | 是否抛给边界取决于配置/代码，本项目首页显式渲染 isError 分支 |
| 访问没有匹配业务路由的 URL               | 本项目通过 '*' 路由显示 NotFoundPage，不等于必然抛出异常     |

### 6.8 首页的接口失败：仍然可以留在当前页面

[源码：HomePage.tsx](../src/pages/home/HomePage.tsx) 的显示判断可以简化为：

```text
feed.isLoading
  → 显示加载占位
否则 feed.isError
  → 显示“动态加载失败”及重新加载按钮
否则存在 posts
  → 显示帖子
否则
  → 显示没有内容的提示
```

这段是结构化说明，实际 JSX 在首页文件中。

重新加载按钮调用：

```tsx
onClick={() => void feed.refetch()}
```

这会重新请求该数据，不等于刷新整个浏览器页面。

首页还有另一个操作：用户主动刷新时间线。

```ts
const handleRefresh = () => {
  if (feed.isRefreshing) return;
  void feed.refresh().catch(() => {
    showToast({
      tone: 'error',
      title: '刷新失败',
      description: '当前内容已为你保留，请稍后重试。',
    });
  });
};
```

它在操作失败时显示 Toast。这进一步说明：**错误呈现方式与操作场景有关，接口失败不一定要把整个页面替换成错误页。**

本阶段不必深挖 feed.refresh 与分页缓存的内部合并逻辑，先认出页面是如何消费 loading/error/data 以及处理操作失败的。

### 6.9 不用破坏入口文件，也能观察失败行为

阅读并运行现有测试：

```powershell
npm run test -- src/app/bootstrapApplication.test.ts src/app/bootstrapFailure.test.ts
```

运行位置是项目根目录。测试中的 `Promise.reject(failure)` 就是在可控地模拟模块加载失败；不需要把真实入口文件删掉。

测试用例也验证了旧内容替换、按钮焦点、监听器只调用一次、元素归属正确 document 等行为。

本项目的回退仍有范围：如果 main.ts 自身或它的静态依赖根本没有成功加载，bootstrapApplication 可能还没有机会执行，不能把这个 catch 当作所有白屏故障的万能处理器。同样，如果回退渲染或 reportError 自己抛错，也不是由这一层 catch 再自动修复。

## 七、动手实验：让 URL 记住页面视图

本实验把现有首页作为练习页，加入“紧凑 / 详细”两种视图，不创建新的路由。当前真实源码还没有这里的 view 功能，下面是供你动手添加的完整示例。你将完成以下行为：

- `/home` 默认展示详细帖子卡片。
- `/home?view=compact` 展示紧凑文字列表。
- `/home?view=detailed` 也展示详细视图；通过按钮切回详细时删除 `view`，用缺省值表达默认状态。
- 切换视图时保留原来的 `tab` 及其他查询参数；切换首页 tab 时也保留 `view` 及其他参数。
- 刷新、复制链接、新标签页打开、后退和前进，都根据当时的 URL 恢复视图。

### 7.1 先理解“状态放在 URL”是什么意思

比较下面两个地址：

```text
/home?tab=following&view=compact
/home?tab=for-you&view=compact
```

它们的 pathname 都是 `/home`，因此匹配 [router.tsx](../src/app/router/router.tsx) 中同一条 `path: 'home'`，加载同一个 [HomePage.tsx](../src/pages/home/HomePage.tsx)。`?` 后面的查询参数由 HomePage 自己读取：`tab` 决定读哪个时间线，新增的 `view` 决定怎样显示同一份帖子数据。

本实验的数据流是：

```text
用户点击按钮
    → setSearchParams 更新地址栏
    → React Router 通知 HomePage 重新渲染
    → params.get('view') 读取新值
    → JSX 选择紧凑列表或详细卡片
```

这里不再添加 `useState('detailed')` 作为视图的唯一来源。单独保存在组件 state 中的值不会自然出现在可复制的地址里；刷新后组件重新创建，也不会自动知道之前选了什么。如果既在 URL 又在 state 保存一份，还需要处理两份值不同步的问题。这个功能直接从 URL 推导值即可。

这不意味着项目不能用 useState。展开菜单、正在输入但尚未提交的文字等临时交互依然适合本地状态。判断标准是：**这个状态是否需要由链接表达，并随浏览器历史恢复？**

### 7.4 第一处：从 URL 读取视图，并提供保留参数的修改函数

找到 HomePage.tsx 中从 `export function HomePage()` 开始，到 `const posts = ...` 结束的这段：

```tsx
export function HomePage() {
  const [params] = useSearchParams();
  const { showToast } = useToast();
  const tab: FeedTab = params.get('tab') === 'for-you' ? 'for-you' : 'following';
  const feed = useFeed(tab);
  const posts = feed.data ? mergeCursorItems(feed.data.pages) : [];
```

把这段整体替换为下面的代码。原先紧随其后的 `const handleRefresh = () => {` 及其后续代码继续保留：

```tsx
type HomeView = 'compact' | 'detailed';

export function HomePage() {
  const [params, setParams] = useSearchParams();
  const { showToast } = useToast();
  const tab: FeedTab = params.get('tab') === 'for-you' ? 'for-you' : 'following';
  const view: HomeView = params.get('view') === 'compact' ? 'compact' : 'detailed';
  const feed = useFeed(tab);
  const posts = feed.data ? mergeCursorItems(feed.data.pages) : [];

  const changeView = (nextView: HomeView) => {
    setParams((currentParams) => {
      const nextParams = new URLSearchParams(currentParams);

      if (nextView === 'detailed') {
        nextParams.delete('view');
      } else {
        nextParams.set('view', 'compact');
      }

      return nextParams;
    });
  };

  const homeTabHref = (nextTab: FeedTab) => {
    const nextParams = new URLSearchParams(params);
    nextParams.set('tab', nextTab);
    return `${paths.home}?${nextParams.toString()}`;
  };
```

逐句理解：

| 代码                                            | 含义                                                                                                                    |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `type HomeView = 'compact' \| 'detailed'`       | TypeScript 字符串联合类型，只允许代码传这两个值；它不会自动校验地址栏中的文本。                                         |
| `const [params, setParams] = useSearchParams()` | 数组解构：第一个值读取当前查询参数，第二个函数更新查询参数并导航。                                                      |
| `params.get('view') === 'compact' ? ... : ...`  | 三元表达式。只有精确的 compact 才选紧凑；缺少、空值、detailed 或未知值都选详细。                                        |
| `new URLSearchParams(currentParams)`            | 复制当前整份查询参数，避免修改原对象，也避免把 tab 和其他参数弄丢。                                                     |
| `delete('view')`                                | 切回详细时删除这个键；因为详细是默认值，链接可以更简洁。                                                                |
| `set('view', 'compact')`                        | 只新增/替换 view；其余键仍保留。                                                                                        |
| `setParams((currentParams) => ...)`             | 更新函数接收当前查询串，再返回新查询串。不要照搬 React state 的“同一轮可累积多次排队更新”假设；此处每次点击只调用一次。 |
| `homeTabHref(nextTab)`                          | 复制当前参数，只改 tab，再构造首页链接，因此切换 tab 不会清除 view。                                                    |

`setParams` 此处没有传 `{ replace: true }`，使用新增历史记录的导航方式。用户每次切到另一个视图后，可以后退到之前的 URL。若使用 replace，会覆盖当前历史条目，不适合本实验要观察的历史切换。

非法值的策略是**显示时回退**，不是自动改写 URL。例如打开 `?view=banana` 时显示详细视图，地址仍保留 banana，便于观察输入。不要额外添加 effect 去反复“修正”地址；本练习只需要一个明确的读取规则。

### 7.5 第二处：让原来的两个 tab 链接也保留查询参数

原来的 tab 链接从零拼出 `?tab=...`。如果只完成上一处，点击 tab 仍会把 view 清掉，因此两处 `to` 都要一起修改。

替换为：

再把：


### 7.6 第三处：插入两个视图按钮

在原文件中找到唯一的 `<QuickCompose />`。在它**紧前面**插入以下完整 JSX，放在外层 `<Stack>` 内，与 QuickCompose 平级。上方原有 tab 工具栏的关闭 `</div>` 保留：

```tsx
<div
  role="group"
  aria-label="首页视图"
  style={{ display: 'flex', alignItems: 'center', gap: 8, flexWrap: 'wrap' }}
>
  <span>显示方式：</span>
  <Button
    type="button"
    size="sm"
    variant={view === 'detailed' ? 'primary' : 'secondary'}
    aria-pressed={view === 'detailed'}
    onClick={() => changeView('detailed')}
  >
    详细
  </Button>
  <Button
    type="button"
    size="sm"
    variant={view === 'compact' ? 'primary' : 'secondary'}
    aria-pressed={view === 'compact'}
    onClick={() => changeView('compact')}
  >
    紧凑
  </Button>
  <span aria-live="polite">当前视图：{view === 'compact' ? '紧凑' : '详细'}</span>
</div>
```

你不需要添加 import，因为当前 HomePage 已经导入 `Button`、`Link` 和 `useSearchParams`。

这里有几处初学者容易混淆的语法：

- `<div>`、`<span>` 是小写 HTML 元素；`<Button>` 是大写 React 组件，最终由它内部渲染原生 button。
- 标签之间的“详细”“紧凑”是组件的 children，也就是按钮里显示的文字。
- `onClick={() => changeView('compact')}` 传入函数，等待点击时才执行；如果直接写 `onClick={changeView('compact')}`，函数会在渲染时执行，行为和类型都不对。
- `{view === 'compact'}` 是 JSX 花括号中的 JavaScript 表达式，计算结果是 true/false。
- `style={{ ... }}` 有两层花括号：外层表示进入 JavaScript，内层是一个对象。它不是 CSS 字符串；`alignItems`、`flexWrap` 用驼峰命名。
- `aria-pressed` 向辅助技术描述该切换按钮是否选中；视觉上的 primary/secondary 则由现有 Button 样式控制。`aria-label` 为整组控件命名。
- `aria-live="polite"` 允许视图状态文案变化被辅助技术平缓宣告；它不负责更新状态，真正的状态仍来自 URL。

### 7.7 第四处：让帖子列表真正改变外观

找到原先 `posts.length ? (` 后面的列表。原代码是：

```tsx
<div style={{ display: 'grid', gap: 14 }}>
  {posts.map((post) => (
    <PostCard key={post.id} post={post} />
  ))}
</div>
```

只把这整个 div 替换为以下内容。外面的 LoadingRows、错误 Notice、空列表 Notice 和“加载更多”分支保留：

```tsx
<div style={{ display: 'grid', gap: view === 'compact' ? 8 : 14 }}>
  {posts.map((post) =>
    view === 'compact' ? (
      <Link
        key={post.id}
        to={paths.post(post.postKind === 'REPLY' ? post.id : (post.contentPostId ?? post.id))}
        style={{
          display: 'block',
          padding: '12px 16px',
          color: 'var(--color-text)',
          background: 'var(--color-surface)',
          border: '1px solid var(--color-border)',
          borderRadius: 12,
        }}
      >
        <strong>{post.author.displayName}</strong>
        <p
          style={{
            marginTop: 4,
            overflow: 'hidden',
            whiteSpace: 'nowrap',
            textOverflow: 'ellipsis',
          }}
        >
          {post.content || '这条帖子包含媒体或链接，点击查看详情。'}
        </p>
      </Link>
    ) : (
      <PostCard key={post.id} post={post} />
    ),
  )}
</div>
```

这里使用 `map` 把帖子数组变成一组 React 元素。每个元素都使用稳定的 `post.id` 作为 key；React 用它区分相邻列表项。紧凑分支渲染作者和单行正文摘要，详细分支继续复用原来的 PostCard。没有复制服务器数据，也没有修改请求：`useFeed(tab)` 仍然只由原来的 tab 决定。

正文里的 `||` 表示在 content 是空字符串等假值时使用后面的提示。`??` 则仅在 contentPostId 是 null/undefined 时使用 id。链接保留现有帖子卡片的详情目标约定：回复使用自己的 id，其他帖子优先使用 contentPostId；第二阶段只需要知道它在复用既有导航规则。

紧凑分支是本实验新写的简化展示，没有自动继承 PostCard 的点赞按钮、媒体预览和曝光上报等功能。它通过详情链接让用户继续阅读。本实验验证 URL 状态与渲染，不把这个简化链接当成完整业务卡片的正式替代。

### 7.8 按矩阵验证，不只看按钮变色

| 操作                                           | 预期 URL 或参数                                 | 预期界面           | 检查重点                     |
| ---------------------------------------------- | ----------------------------------------------- | ------------------ | ---------------------------- |

| 打开 `/home?view=` 或 `/home?view=COMPACT`     | 不自动改写地址                                  | 详细               | 空值和大小写规则             |

| 复制紧凑视图完整 URL，在新标签页打开           | URL 带原查询参数                                | 会话满足守卫后紧凑 | 分享的是状态，不只是首页地址 |
| 从紧凑点击详细                                 | 只删除 view，tab/probe 保留                     | 详细卡片           | 默认状态的简洁 URL           |
| 执行下面的历史顺序                             | URL 与视图逐步同步                              | tab 和视图同时恢复 | push 历史行为                |

历史测试务必在**同一个标签页连续点击**，不要每步都手动输入地址：

```text
A. 打开 /home?tab=following&probe=keep      → 正在关注 + 详细
B. 点击“紧凑”                            → 正在关注 + 紧凑
C. 点击“为你推荐”                        → 为你推荐 + 紧凑
D. 点击“详细”                            → 为你推荐 + 详细

点一次浏览器“后退”                       → C
再点一次“后退”                           → B
点一次“前进”                             → C
再点一次“前进”                           → D
```

每次不仅看“当前视图”文字，还看地址栏、选中的 tab，以及列表是简短文本还是完整卡片。如果只变 URL 不变页面，检查 view 是否仍从 params 推导；如果 tab 切换后丢 view，检查第二处两个 Link 是否都已修改。

复制链接不会复制登录凭证或权限。真实 API 模式中，接收链接的人必须先满足认证/引导条件，才能看到首页；URL 状态解决的是视图恢复，不是身份授权。Mock 中新标签页容易直接恢复固定用户，正是两者最容易被混淆的地方。

## 八、综合自测与答案

每题先用自己的话作答，再核对答案。重点是解释“哪一层在什么时候做什么”，而不是背文件名。

### 题 1：浏览器如何从 index.html 走到首页？为什么不能跳过 root？

**答案：**[index.html](../index.html) 提供 `<div id="root"></div>`，并加载 [main.ts](../src/app/main.ts)。main.ts 导入全局样式，调用 [bootstrapApplication](../src/app/bootstrapApplication.ts) 查找挂载点并动态加载 [mountApplication](../src/app/mountApplication.ts)。后者按环境决定是否先启动 Mock，再创建 React root 并渲染 [ApplicationRoot](../src/app/ApplicationRoot.tsx)。ApplicationRoot 组合 Provider 和 AppRouter；路由根据 URL 匹配页面，守卫决定是否允许页面继续显示，布局通过 Outlet 放入页面。root 是 React 挂载的实际 DOM 容器；当前实现找不到它时只报告错误并返回 missing-root，没有可用容器去显示普通启动回退面板。

### 题 2：为什么先等待 Mock Worker，再调用 React 的 render？

**答案：**React 挂载后，认证 Provider 和页面可能开始发请求。提前等待 Worker，能让这些初始请求受 Mock 拦截；如果顺序相反，请求可能先进入真实网络。具体顺序见 [mountApplication.ts](../src/app/mountApplication.ts) 的 `await enableMocking()`，然后才是 `createRoot(root).render(...)`。

### 题 3：设置 VITE_ENABLE_MOCK=true，就能保证任意构建都开启 Mock 吗？

**答案：**不能。启动代码要求 Mock 开关为 true，且满足 `import.meta.env.DEV` 或 `import.meta.env.MODE === 'test'`。普通 production build 不满足后一组条件。变量还要经过 [env.ts](../src/shared/config/env.ts) 的 Zod 解析；编译时模式、应用的 VITE_APP_ENV 字符串和 Mock 开关是不同概念。

### 题 4：HomePage 没有创建 QueryClient，为什么能调用 useFeed？Toast 又来自哪里？

**答案：**它位于 [AppProviders](../src/app/providers/AppProviders.tsx) 的后代树中。QueryClientProvider 向其后代提供共享 [queryClient](../src/shared/api/queryClient.ts)，useFeed 内部使用 Query hooks 时能取得这个上下文；ToastProvider 提供 showToast 和全局提示容器。其主要包裹顺序是 QueryClientProvider → ToastProvider → AuthBootstrap → RealtimeProvider → AppRouter。Provider 通过组件树提供能力，不要求每页都重新创建相同服务；它也不是把 HTML 写进每个页面文件。

### 题 5：/users/alice?view=compact 中，alice 与 compact 有什么不同？

**答案：**alice 对应 `users/:handle` 的路径参数，用于标识访问哪一个用户；compact 是查询参数，只有读取它的页面才会赋予它意义。当前实验只在 HomePage 读取 view，所以把 `view=compact` 放到用户页不会自动让用户页也变紧凑。React Router 根据路径匹配路由，业务组件决定怎样使用查询参数。

### 题 6：AppShellLayout 中删掉 Outlet，侧栏还可能在，但首页内容为什么不见？

**答案：**父路由匹配到 AppShellLayout 时，它负责渲染 Sidebar、Topbar 和 MobileNavigation；[Outlet](../src/app/layouts/AppShellLayout.tsx) 是匹配子路由页面进入父布局的插槽。删掉这个插槽，外壳本身仍可渲染，但 HomePage 没有被放进布局。不是 HomePage 自动去寻找某个 CSS 类名或 DOM id 再插入。

### 题 7：访问 /home 时，四种认证状态分别显示什么？

**答案：**依 [guards.tsx](../src/app/router/guards.tsx)：

| 状态                       | 首页守卫的行为                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------- |
| bootstrapping              | 显示“正在恢复会话”，等待结果                                                            |
| anonymous                  | replace 跳到 /auth/login，state.from 保存原 pathname + search                           |
| authenticated 且引导未完成 | 按 onboardingStatus 跳到对应引导页，例如 PENDING_RECOMMENDED_USERS → /onboarding/follow |
| authenticated 且引导已完成 | 返回 children，显示 AppShellLayout 与匹配的首页                                         |

前端守卫决定用户看到什么界面，后端仍必须独立校验接口权限。手动改前端状态不会赋予真实服务端访问权。

### 题 8：直接打开 /auth/login 与 /settings/profile，为什么外壳不同？

**答案：**router.tsx 中 auth 子树使用 [PublicLayout](../src/app/layouts/PublicLayout.tsx)，登录表单进入其 Outlet；settings/profile 位于 RequireCompletedOnboarding 包裹的 [AppShellLayout](../src/app/layouts/AppShellLayout.tsx) 子树，因此显示主导航和顶栏。布局由路由树的父节点决定，不是通过 URL 字符串包含 login 来随意换一个 CSS 背景。

### 题 9：为什么把 view 写成 useState('detailed') 不够？只从 URL 初始化一次 useState 呢？

**答案：**纯组件 state 不会随链接分享；刷新时初始值又是 detailed。即使首次使用 URL 初始化 state，浏览器后退/前进改变查询串时，该 useState 初始化器也不会因此重新初始化，仍可能显示旧视图。本实验每次渲染直接从 useSearchParams 读取 view，因此地址变化与视图选择保持一致，不需要再同步一份本地副本。

### 题 10：点击紧凑后，为什么不能写 setParams({ view: 'compact' }) 就结束？

**答案：**那是在提供一份新的查询参数对象，原有 tab、probe 等不会自动合并进去。本实验先 `new URLSearchParams(currentParams)` 复制整份参数，再修改 view。相同原则也用于原 tab 链接：不能继续从零拼出 `?tab=following`，否则反方向切换又会丢 view。

### 题 11：三个错误场景分别应该去哪里找？

**答案：**

| 场景                                                 | 当前工程的处理层                                                                                                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动阶段动态导入失败，或 mountApplication 返回拒绝   | bootstrapApplication 的 catch 调用 [renderBootstrapFailure](../src/app/bootstrapFailure.ts)，用原生 DOM 显示“应用暂时无法启动”，不依赖 React 正常工作 |
| 已进入路由系统，路由 lazy 加载或匹配路由元素渲染出错 | 根路由的 errorElement 使用 [RootErrorBoundary](../src/app/error/RootErrorBoundary.tsx) 显示路由错误和重新加载入口                                     |
| 首页信息流请求失败，被 useFeed/Query 记录为错误状态  | [HomePage](../src/pages/home/HomePage.tsx) 的 feed.isError 分支显示“动态加载失败”和重新加载按钮，属于页面自己的失败界面                               |

不是所有错误都会自动冒到 RootErrorBoundary：页面主动处理的 Query 错误通常继续留在页面；事件回调或异步任务中的任意异常，也不等于路由边界必然接管。启动函数中的 try/catch 也不是所有以后发生的 React 错误的通用捕获器。

### 题 12：访问一个不存在的地址，会自动显示 RootErrorBoundary 吗？

**答案：**本路由树显式定义了 `path: '*'`，匹配后加载 [NotFoundPage](../src/pages/not-found/NotFoundPage.tsx)。这是正常的兜底路由页面，不等于抛出了路由异常。只有加载或渲染该页面本身又失败，才会涉及相应错误边界。

### 题 13：Mock 退出后刷新又进首页，能证明 AuthBootstrap 或守卫出错吗？

**答案：**不能。当前 Mock refresh 无条件返回固定已完成引导会话，而 logout 不维护真实会话吊销状态。刷新使前端重新启动，AuthBootstrap 再请求 refresh，便可能恢复固定用户。应先识别数据来源，再用 [guards.test.tsx](../src/app/router/guards.test.tsx) 中显式设置的状态研究守卫分支；真实模式需结合实际 Cookie、refresh 响应和后端会话判断。

### 题 14：复制 /home?tab=for-you&view=compact 给别人，哪些东西会被复制，哪些不会？

**答案：**复制的是页面路径、时间线选择与视图选择，没有复制 React 内存、Query 缓存、身份 token 或访问权限。对方满足守卫后，HomePage 可以从 URL 得知要看 for-you 和 compact，再按自己的会话读取数据。所以“视图可分享”不等于“所有人都能看到完全相同的私人数据”。

### 题 15：如何证明这次 URL 练习完成，而不是“看起来能切换”？

**答案：**至少要有：默认/合法/非法值行为可解释；切换 view 保留 tab 和其他参数；切换 tab 也保留 view；刷新和新标签页能恢复；同一标签页的后退/前进同时恢复 tab 与视图；代码检查的实际结果已记录。已有启动和守卫测试可以验证它们原本覆盖的行为，但不会自动覆盖新写的 HomePage 分支。未执行的命令保持“待执行”，不要写成“已通过”。
